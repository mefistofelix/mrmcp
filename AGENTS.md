# MrMCP implementation guide

## Current release and files

MrMCP 0.10.120 consists of seven root project files, one GitHub Actions workflow and one versioned asset directory:

- `mrmcp.js` — Deno backend, MCP `2026-07-28`, OAuth/Basic authentication, SQLite, local Tauriless UI and desktop launcher.
- `commands.yaml` — versioned editable extra-command catalog; keep it in the repository root, never under `assets/`.
- `guided_prompts.yaml` — versioned editable MCP guided-prompt catalog; keep it in the repository root, never under `assets/`.
- `README.md` — concise current user/operator behavior only; keep release history out of it.
- `CHANGELOG.md` — release history only.
- `AGENTS.md` — implementation invariants and release checks.
- `TOOLS.md` — current built-in tool contracts, arguments, semantics and design rationale.
- `.github/workflows/release.yml` — tag-driven GitHub release automation. It must verify `VERSION == tag`, use Deno 2.9.5, build Windows x64 and Linux x64 standalone executables plus native macOS x64/arm64 `MrMCP.app` bundles on matching macOS runners, then create compressed `.dmg` disk images and create/update the GitHub Release with exactly four project-built assets: the two portable binaries and the two DMGs. Do not add checksum/tar/zip archives.
- `assets/` — all static WebView/build assets, including `morphlex.js`, vendored `jsoneditor/` (minimalist JS/CSS/icon plus license), `mrmcp-logo.svg`, `mrmcp-logo.png`, `mrmcp.ico` and the numbered administration screenshots; do not duplicate them in the repository root.

The only public MCP protocol endpoint is `/mcp`. The public HTTPS listener also serves the read-only unauthenticated `/mrmcp-icon.png` branding asset referenced by MCP `serverInfo.icons`. The administration UI is local-only through Tauriless' `tauri` asset protocol and opens no GUI network listener.

## Desktop shell

MrMCP must not import or call Sharp directly. CDP screenshot post-processing uses the public `auto.vips.decodeImage` / `auto.vips.encodeImage` API exported by the installed Auto.js package; never import Auto.js `vips.js` by path. `format=original` performs no image-codec load, while `format=webp` uses that public layer and its current fixed WebP Q=80 plus optional scale. Auto.js is deliberately one normal unversioned latest static `import * as auto from "npm:@mefistofelix/auto.js"`. `desktop_auto` is the only MCP desktop-automation surface: it accepts one AAF YAML scenario and passes it to `auto.run()`; do not expose Auto.js primitives as separate MCP tools or invent a second automation DSL. Preserve arbitrary `results`/final `state`; when final state contains retained WebP/PNG images, recursively keep each image at its original nested state location, remove only binary `data`, insert an `image_id`, deduplicate shared image objects, and emit each distinct image as an MCP `ImageContent` block after the structured JSON text block. These transient model-observation images must never use `publish`, Published storage, MCP Apps or `resource_link`; WebP/PNG plus Auto.js `scale` controls MCP's Base64 wire cost, while AAF `rect` remains absolute screen-space coordinates. Load Tauriless only through the unversioned latest npm literal dynamic import `await import("npm:@mefistofelix/tauriless")` inside `desktop()`, after the backend Worker has started. Never restore a top-level Tauriless import: Tauriless eagerly calls `Deno.dlopen` during module evaluation, so the same `mrmcp.js` being evaluated by the main isolate and backend Worker would load the native bridge twice in one process; on macOS that can register duplicate Objective-C classes and break WebView bootstrap. Resolve Tauriless from npm latest at check/build time and configure desktop identity before the first WebView through the single cross-platform `tauriless:set-app-user-model-id` bridge.

- Do not add a hand-written FFI wrapper, vendored Tauriless native binaries, a Rust/Tauri scaffold, Neutralinojs, a Node.js application, npm project files or a separate CLI scaffold. The only command-line modes are the normal desktop launch, `--backend`, and one-shot `--add-workspace <name> <path>` handled directly by `mrmcp.js`. Tauriless is consumed only as the normal npm JS library and owns its native binding internally.
- Desktop mode is one OS process: Tauriless stays on the main OS thread and Deno repeatedly calls `tauriless.run(16)`, giving the native event loop a bounded 16 ms slice before Deno resumes its own event loop; the backend runs in a named Deno Worker/isolate loaded from the same `mrmcp.js`. Readiness and shutdown use typed Worker messages (`ready`, `shutdown`, `stopped`), not stdout parsing or a child process. Tauriless serves the GUI through `asset-request` / `tauriless:asset-response` with inline `content`; the GUI has no loopback HTTP listener, login token, cookie, session or CSRF layer. Browser inputs use Tauri `plugin:event|emit`; Deno renders in the Worker, posts the render to the main thread, and the main thread delivers it with `plugin:event|emit_to`. The WebView must register `tauri://close-requested` immediately with the static `main` Window target so Tauri does not destroy the window, but this listener is independent from the MrMCP render-event/bootstrap chain: never gate GUI bootstrap on it and never read `__TAURI_INTERNALS__.metadata.currentWindow` during startup. The Tauriless main-thread drain remains responsible for reacting to the forwarded close request by hiding `main`. The main thread also owns native window visibility detection and sends typed `ui-visibility` messages to the Worker. Hidden or minimized windows must not cause backend UI projection, Eta rendering, HTML construction or Worker→WebView render delivery; Deno state/data still updates and the render queue remains dirty until one fresh full-state render is requested when the window becomes visible and non-minimized again. Closing the Tauriless window requests graceful backend shutdown and then terminates the Worker only as a bounded fallback. Worker wait timeouts must clear their timers when readiness/shutdown wins; after desktop cleanup completes, the main entrypoint exits explicitly so FFI or other residual handles cannot keep `mrmcp.exe` resident.
- The initial desktop size is 1180×760.
- Release builds target Windows x64, Linux x64, macOS x64 and macOS arm64. Windows/Linux are produced on Linux; macOS builds run natively on `macos-15-intel` / `macos-15`, package the standalone executable as `MrMCP.app`, then place that bundle plus an `Applications` link inside a compressed read-only `.dmg`. The Tauriless npm latest package must bundle `win32-x64`, `linux-x64`, `darwin-x64` and `darwin-arm64` native bridges. Because Deno 2.9 applies a default 24-hour minimum dependency age, release CI must pass `--minimum-dependency-age=0` to check/compile so the current npm latest dependencies can be consumed immediately. Windows standalone builds must use both `deno compile --no-terminal` and `--icon assets/mrmcp.ico` so the compiled desktop application opens only the WebView, has the MrMCP executable icon and does not create a companion console window. Never omit either flag from release builds. After any local source change that can affect the standalone application, always regenerate the local `mrmcp.exe` before finishing so the current build is immediately testable; do not leave source and executable out of sync. Each macOS DMG must mount in Finder and contain one `MrMCP.app` with executable `Contents/MacOS/MrMCP`, `Info.plist`, `Resources/MrMCP.icns`, plus an `Applications` symlink; the app bundle must carry a valid ad-hoc code signature unless Developer ID signing/notarization is deliberately configured. Do not add runtime console-hiding code; source-mode `deno run` remains terminal-attached for development.
- Keep the native desktop integrations enabled: set the main window icon through `plugin:window|set_icon` using in-memory RGBA data; create one MrMCP tray icon whose menu contains only Quit; attach the menu event channel to the Quit item itself and identify menu/tray actions from their event payloads, never from hard-coded Tauri callback/channel ids; a left tray click toggles the main window visible/hidden and does not open the menu, but if the window is minimized it restores and focuses it instead of hiding it; a normal window close request hides the window instead of terminating MrMCP. Enable native window drag/drop: dropped directories are forwarded to the backend and automatically added as enabled Workspaces, dropped non-directories are ignored, and a path already represented by any Workspace is a no-op. Auto-created Workspace names start from the final directory name and use the first free `Name`, `Name #2`, `Name #3`, ... form. Workspace names are globally unique database keys through `UNIQUE(name)`. Desktop OS notifications are independently controlled by persisted Session, Workspace and Tool Call settings, each enabled by default and initially falling back to the legacy global value on existing installs until the per-type values are saved. Session notifications represent logical lifecycle events: **New Session** when a Session is first created, **Session Active** when a Session starts a Tool Call after at least 10 minutes without one, and **Workspace Opened** whenever `open_workspace` successfully attaches that Session to a Workspace. Incoming valid Tool Calls use the Tool Call setting. Invalid/rejected Tool Calls receive an outcome notification instead of a duplicate generic start notification, and valid Tool Calls that later fail receive an additional final failure notification. Successful native directory-drop additions and dropped directories that already correspond to existing Workspaces use the Workspace setting; one drop produces one notification summarizing added and already-existing Workspaces. The desktop shell already supplies the MrMCP application identity, so notification titles must never redundantly prefix `MrMCP`. Every notification body that names a Session must use the same easy-to-scan multiline identity: `💬 Session #<id>`, then list lines for `📁 <Workspace>`, `🕒 <creation age>` and `🛠️ <N> Tool Calls`. Use emoji-led event titles such as `✨ New Session`, `🟢 Session Active`, `📂 Workspace Opened`, `🛠️ Tool Call #<id>`, `⚠️ Invalid Tool Call #<id>` and `❌ Tool Call Failed #<id>`; the Tool Call number belongs in the notification title, not beside the tool name in the body. For Tool Call notifications, put the shared compact `tool · args` summary on the first body line so Windows toast truncation cannot hide it; put the Session identity immediately after that summary, then progress/error details. Invalid/failure bodies append one compact `⚠️` error line after tool/command details. When the original MCP request supplied `_meta.progressToken`, every Tool Call start/outcome notification also appends `📡 Progress requested`; do not place that transport flag inside the tool argument preview. Use bullets/newlines when a notification contains multiple facts or Workspace names. The Tauriless main thread performs every native notification call. After the drain loop starts but before the first WebView exists, every desktop platform must call the single cross-platform `tauriless:set-app-user-model-id` command with `{ appId: "com.mefistofelix.mrmcp", name: "MrMCP" }`. Tauriless uses that value as Tauri's application identifier everywhere and performs the additional Windows shortcut/AppUserModelID registration only on Windows. Notifications continue through the unmodified `plugin:notification|notify` command; the Tauriless npm latest package must build Tauri with production/custom-protocol behavior so macOS notification identity is the configured MrMCP bundle identifier rather than development Terminal identity. On macOS, resolve notification authorization lazily on the first actual notification with `plugin:notification|is_permission_granted` followed by `plugin:notification|request_permission` only when needed, cache that result for the desktop run, suppress delivery after denial, and do not flush startup notifications until the main window is visible. Other platforms keep their existing notification path. The macOS tray must set `iconAsTemplate: true`; other platforms may pass false.
- Keep WebView/static resources in `assets/`. The desktop GUI may inline the small CSS/JavaScript/logo payload into the Tauriless asset response; do not reintroduce GUI HTTP routes merely to serve them. The only public branding path is exact HTTPS `GET /mrmcp-icon.png`, backed by `assets/mrmcp-logo.png`, so MCP clients can fetch `serverInfo.icons` without credentials. Source mode reads assets from disk; standalone builds embed them with `deno compile --include assets` so the same files resolve from Deno's virtual filesystem.
- Never modify third-party/vendor libraries, including `assets/morphlex.js`, without explicit user approval. Use the library's public API, callbacks and extension points from MrMCP-owned code instead.
- Keep `commands.yaml` in the repository root, not `assets/`. Source mode reads/writes that physical file directly. Standalone builds must additionally compile with `--include commands.yaml`; treat the embedded copy only as a first-run template. Portable executables materialize it beside the executable when absent. A macOS standalone detected inside `*.app/Contents/MacOS` must instead use `~/Library/Application Support/MrMCP/` as `APP_DIR`, placing `commands.yaml` there and `.mrmcp` beneath it so runtime state never mutates the application bundle. Never overwrite an existing user-edited `commands.yaml` from the VFS template. The public MCP discovery tool is `discover_commands`: it takes only `context_handle`, returns every currently available command in one non-paginated response with only `logical_name`, description and optional documentation URL, preserving `commands.yaml` order for registered entries and appending any unregistered automatic executables afterward; its descriptor/instructions must tell agents to consult it proactively when extra CLI capability could help, prefer suitable user-provided entries over invented workarounds, reuse the complete catalog for the Session, and invoke logical names directly through `exec` without PATH probing. The Commands GUI also preserves YAML order and defaults to 5 rows per page. Its command-source/state filter is one select with All Commands, Available, Unavailable, YAML Metadata and Disk Only; YAML Metadata means registered in `commands.yaml`, while Disk Only means an executable discovered in `.mrmcp/bin` with no YAML entry. A global Agent Discovery toggle on the Commands page is persisted in the `config` table, defaults enabled, never hides or disables GUI catalog management, and when disabled makes `discover_commands` return only an empty `commands` array while the tool itself remains published.
- Keep `guided_prompts.yaml` beside `commands.yaml` as the sole authoritative guided-prompt store; do not mirror prompt definitions into SQLite. Source mode reads/writes that file directly. Every standalone build must compile with `--include guided_prompts.yaml`, materialize it beside the portable executable only when absent, and use `~/Library/Application Support/MrMCP/guided_prompts.yaml` inside a macOS app bundle without ever overwriting a user-edited copy. Publish the MCP `prompts` capability plus `prompts/list` and `prompts/get`; preserve YAML order and expose each entry's name, optional title/description and flat string arguments. A prompt template is one user text message rendered through a dedicated non-escaping Eta instance with standard `<% ... %>` tags. The template model exposes `args`, prompt metadata, current Session/Workspace only when the prompt explicitly accepts a valid `context_handle`, the available Workspaces, sanitized server/client/request metadata and runtime OS/arch/time paths. Prompt Eta is trusted local configuration and intentionally not sandboxed; never pass authentication secrets or raw request headers into the model. The Guided Prompts GUI manages the YAML catalog directly, defaults to five rows per page and has a Template Help subpage reachable only from Guided Prompts, never from the main sidebar. That Help page must document the canonical YAML shape, Eta syntax, model fields, `context_handle` behavior and trusted-code nature. Keep two small editable starter prompts in the versioned default `guided_prompts.yaml`: one argument-free connector-block debugging example that describes test context truthfully and never claims a blocked action is safe/verified merely to bypass a restriction, and one parameterized project-review example demonstrating ordinary arguments plus optional `context_handle`.
- Direct `--backend` mode is strictly headless: it must never import Tauriless, load WebView-only assets, enqueue GUI renders, post desktop notifications or create any native GUI object. `--add-workspace <name> <path>` is a one-shot database operation: apply the same name/path validation as the GUI, create the current schema/server row if needed, insert one enabled Workspace with the entered path string unchanged, then close SQLite and exit before listener/TLS/process/GUI startup.
- Keep Workspace records conventional: globally unique name, user-entered path, enabled state, edit and delete. The `roots` table remains the internal persistence name, but visible GUI and MCP terminology is always **Workspace**. Workspace paths may be absolute or relative; store the entered path string unchanged in SQLite and resolve relative values against `APP_DIR` only when an operation actually needs an absolute path. Validate Workspace and Command path existence/type on blur, never through browser-native validation UI. Field errors render inline beside the relevant field and disable Save; generic operational errors use a small Deno-owned on-screen balloon, never an error modal/alert popup. Session-to-Workspace reassignment belongs on the Workspaces page through server-routed drag/drop; do not put a Workspace selector back on Sessions. Session drag items keep Session id/client on the first line and Created, Last Activity, Status and `Tool Calls: N` together underneath; do not repeat generic OAuth/auth-kind text there.

## Database: direct current schema, no versioning

The repository is in development. There is no backward-compatibility layer and there is no database schema-version concept.

1. Do not introduce `DB_SCHEMA_VERSION`, `PRAGMA user_version` checks or any equivalent version gate.
2. Prefer extending an existing logical table over creating auxiliary tables whose only purpose is compatibility or carrying fields that naturally belong on that table. Do not create a separate compatibility table when adding columns to the existing table is the simpler current-schema design. Ensure genuinely distinct current tables/indexes directly at startup with `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`.
3. Do not add schema-version migration frameworks or backfills. When an existing current table is missing newly required columns, add those columns idempotently at startup with conditional `ALTER TABLE ... ADD COLUMN` when that is semantically appropriate, then validate the resulting current schema immediately afterward.
4. Keep required-column checks tied to structures the current code actually needs; if an existing table has an incompatible shape, fail on that shape and tell developers to recreate `.mrmcp/mrmcp.sqlite`.
5. Never import legacy configuration keys or identifiers.
6. Never retain an old table or column only for compatibility.
7. Never accept legacy `opaque_` values, `server_opaque` arguments or transport-derived session identifiers.
8. A clean schema must create no named `default` Workspace and `roots.name` must be globally unique with `UNIQUE(name)`, never `UNIQUE(server_id,name)`.
9. `contexts.id` is the numeric administrative Session primary key; `contexts.handle` remains the unique opaque Session bearer capability. Tool-call and process rows retain both `context_id` and `context_handle` snapshots. `process_runs.log_id` stores the originating Tool Call id for every managed process; for `exec_start` that same integer is the public `exec_id` used by follow-up exec tools and by Tool/command filtering. HTTP diagnostic rows keep their historical Session/Workspace association in additive `debug_log_workspaces(debug_log_id PRIMARY KEY, context_id, root_id, root_name, root_path)` with `ON DELETE CASCADE`; the HTTP Log must never derive a historical Workspace label from the Session's later current `root_id`. Context rows may also retain observational creation-client metadata (`auth_kind`, OAuth client id/name and User-Agent); that metadata never owns or authorizes the Session. Keep Tool Call transport metadata separate from tool arguments in additive `tool_call_transport(log_id PRIMARY KEY, progress_requested)` with `ON DELETE CASCADE`; `input_json` remains the exact tool argument object. `logs.id` is also the public persistent-execution `exec_id` returned by `exec_start`; therefore its SQLite AUTOINCREMENT sequence must never be reset or reused during the lifetime of a server data directory.
10. Settings **Clear Operational Data** is a history/data cleanup, not a configuration reset: preserve `config`, `server_config`, `custom_tools`, all OAuth tables, `roots`, `contexts`, `memories`, `cdp_browsers`, `cdp_targets` and the persistent `.mrmcp/cdp/` browser profiles; clear Tool Call rows plus `logs_fts`, descriptor/transport metadata, `process_runs`, HTTP log rows plus Workspace snapshots, every row in shared `published` plus its `.mrmcp/publish/` payload snapshots, and reset metrics. After the deletion transaction commits, run `VACUUM` followed by `PRAGMA wal_checkpoint(TRUNCATE)` so freed SQLite pages and WAL storage are returned to disk. Reset the `debug_logs` sequence only; never reset the `logs` sequence because live detached executions may still hold those ids and future `exec_id` values must remain unique/monotonic. Page-level confirmed Clear actions are also required: Tool Calls clears Tool Call/search/descriptor/transport/process-history records without resetting Tool Call ids or stopping already-detached persistent processes; Sessions deletes every Session after draining in-flight Tool Calls and requests termination of running persistent processes owned by those Sessions while preserving Tool Call history snapshots; Workspaces deletes every named Workspace and moves Sessions to root id `0` without touching files or running processes; OAuth Clients removes all OAuth clients/codes/access/refresh tokens while preserving Sessions and Basic authentication; HTTP Log clears HTTP rows plus `debug_log_workspaces`. Dashboard **Empty Trash** permanently removes only the contents of the single `APP_DIR/.mrmcp/trash` store. Tool-Call-dependent maintenance uses one Promise barrier rather than an application queue: new Tool Calls wait, already in-flight Tool Calls finish, maintenance runs, then waiting Tool Calls continue. Maintenance dialogs are confirmation-only: after Confirm they close immediately; long-running maintenance reports completion/failure through the Deno-owned notice balloon and must never fail only to console. Dashboard always exposes the current `activeCallControls.size` as Tool Calls In Flight. Do not add browser polling or a browser-owned countdown. Clear Operational Data must not delete certificates, command files/catalog data, trash contents or Workspace files outside the dedicated `.mrmcp/publish/` snapshots; Empty Trash must not delete anything outside the managed trash directories.

## MCP 2026-07-28 and explicit Session capabilities

Only protocol `2026-07-28` is advertised and accepted.

The protocol is stateless and sessionless at the transport layer:

- use `server/discover`;
- do not implement a successful legacy `initialize` path;
- do not advertise older protocol versions;
- do not send, consume or infer identity from `Mcp-Session-Id` or vendor session headers;
- every request must be understandable without a previous transport handshake;
- keep one `/mcp` POST endpoint. Ordinary RPCs and foreground `exec`/custom commands without `_meta.progressToken` return one `application/json` response. With `_meta.progressToken` plus SSE acceptance, foreground `exec` and custom commands return request-scoped `text/event-stream`; `exec_attach` may return request-scoped SSE with or without a progress token because its no-progress mode can long-poll. Never add the deprecated persistent HTTP+SSE `/sse`/GET transport;
- request-scoped process progress uses only standard `notifications/progress` for requests that supplied `_meta.progressToken`. Batch normalized combined process output at a hard 16 KiB maximum or 100 ms, whichever happens first; send no empty progress events, flush any remainder before the final JSON-RPC result, then close the SSE response. The final `exec` result always contains the complete transcript; progress is an additional delivery path, not the only copy;
- HTTP content compression belongs to Deno. Both public `Deno.serve` listeners must use `automaticCompression: true`; do not add a hand-written zlib/Brotli/gzip response middleware, `Content-Length` gate, chunk encoder or compressor-flush layer. Deno owns content-encoding negotiation/compressibility and the HTTP runtime owns framing. Current Deno leaves `text/event-stream` uncompressed even when ordinary compressible text/JSON responses negotiate gzip/Brotli; preserve that native behavior rather than adding an SSE-only compressor.

Application state uses an explicit Session bearer capability:

- `list_workspaces` is a sessionless read-only discovery tool. It accepts no `context_handle` and returns only the enabled Workspace names that may be passed to `open_workspace`;
- `tools_schema` is an authenticated sessionless read-only diagnostic tool. It accepts only 1–50 unique exact published tool names and returns their canonical complete descriptors from the same `serverTools()` source used by `tools/list`, plus unresolved names in `missing`. Its published `names[]` schema must declare `uniqueItems: true`, and execution must also reject duplicate names explicitly as a runtime defense. Do not remove valid schema constraints to work around a stale ChatGPT conversation: after changing published tool names or schemas, test the refreshed contract from a new chat/branch because an existing conversation may retain its earlier tool-schema snapshot. Never maintain a second descriptor/schema copy for this tool. Returned publication View resource URIs are canonical; the normal `tools/list` cache-busting `?instance=...` suffix is intentionally dynamic and not schema semantics;
- Workspace creation for agents is folded into `open_workspace(create=true)`; there is no public `create_workspace` tool. The internal Desktop-creation helper remains name-only/path-opaque: resolve the current user's Desktop internally without environment-variable home discovery, derive the final directory solely from the name, reject registered-name/registered-effective-path/existing-filesystem-target collisions before touching the filesystem, create the directory non-recursively, then register one enabled Workspace. If directory creation fails, do not touch the database; if later database insertion fails, leave the created directory in place. Linux honors `~/.config/user-dirs.dirs` `XDG_DESKTOP_DIR`; macOS and the core-only Windows fallback use OS-reported home plus `Desktop`;
- `open_workspace` has no required `context_handle` input; it requires a free-string Workspace `name`, optional `create` default false, and optional `current_context_handle`. A missing/disabled Workspace is an error unless `create=true`; if true and genuinely missing, create it through the internal Desktop helper, then open it. An active current handle is reused while its Session moves; omitted/empty/unknown/expired creates a new Session. The tool always returns the effective `ctx_...` value;
- `open_workspace` directly returns `workspace_name`, absolute `cwd`, nullable Workspace-level `agent_guidance_path`, `workspace_created`, and a compact `memory_summary` containing live counts plus up to five latest keys for Workspace and Session scope; read guidance when non-null and treat the memory summary only as orientation, not as memory values;
- every other base and custom tool requires the same `context_handle` property;
- every output schema except sessionless `list_workspaces` and `tools_schema` requires `context_handle` as common metadata; `list_workspaces` returns only its Workspace-name list and `tools_schema` returns only `tools` plus `missing`;
- every built-in tool must add an explicit tool-specific output schema and use `additionalProperties: false`; never regress to one permissive generic result schema;
- failed calls set `isError: true` and expose one human-readable `error` string; do not add duplicate status, execution, retry, recovery-tool or log-id fields;
- on tools that require `context_handle`, missing, invalid or expired handles never execute the requested operation and never mint a replacement automatically; `open_workspace` is the deliberate exception for its optional `current_context_handle`, where an unusable value creates a new Session;
- valid handles execute and are repeated byte-for-byte in the result;
- Sessions expire after 30 days without activity.

Authentication gates access to the server. After authentication, `list_workspaces`, `open_workspace` and `tools_schema` may be used without a pre-existing Session; `open_workspace` itself returns/selects the Session capability. For other Session-bound tools, possession of a valid `context_handle` selects the Session and its current Workspace. Do not bind Sessions, managed processes or JavaScript kernels to an OAuth client, Basic credential, owner key or transport identity.

Never describe `context_handle` as a protocol or transport session identifier. Session client metadata is best-effort observational information captured when `open_workspace` creates the Session; do not infer a model, reasoning/thinking level or client ownership from it. A ChatGPT model or thinking-level change may result in a new Session even inside the same chat.

## Authentication and authorization

Authentication is the only server-access decision.

- Authenticated clients receive all published tools.
- Anonymous clients receive none.
- Do not implement tool approvals, allow/deny regular expressions, enable lists, execution switches or per-tool policy rules.
- OAuth consent remains only to authorize the OAuth client.
- The public OAuth consent/error page must remain client-agnostic and server-rendered with the same Eta instance used by the administration UI. Dynamic client, scope, resource, redirect and hidden-form values go through Eta auto-escaping; do not rebuild the page with interpolated HTML strings or client-specific copy. Keep it as a compact centered one-screen card using the administration GUI dark palette, with compact client/scope/resource/return rows, green **Authorize Access**, red **Cancel**, matching branded invalid/expired state, and the direct standards-compliant redirect to the registered client callback after the decision. On desktop keep the panel around half the viewport width and size typography from a combination of `vw` and `vh`; do not derive primary consent typography from `vmin`, because a short landscape viewport makes it unacceptably small. Keep logo, spacing and actions viewport-relative, constrain the document to the viewport, and keep all details and both actions visible without scrolling in a normal desktop viewport. Do not add a separate trust-notice block or redundant footer.
- `context_handle` is a bearer capability shared by any authenticated client that possesses it.

## Workspaces and current working directory

The GUI maintains named Workspaces. Workspace names are globally unique; a Workspace may be assigned to many Sessions, while each Session stores exactly one current internal `root_id`.

- Internal Workspace id `0` is the program-folder fallback containing `mrmcp.js`; it is not a named Workspace accepted by `open_workspace`.
- `open_workspace(name, create?, current_context_handle?)` is the only agent Workspace opener/creator. Its published `name` remains a free `string`, never a dynamic enum. With `create=false` (default), the name must resolve to an enabled Workspace; with `create=true`, a genuinely missing name may be created as exactly one empty Desktop directory through the internal name-only/path-opaque helper before opening. Existing Workspaces are never replaced. With an active current handle it reassigns that same Session immediately and preserves the handle; otherwise it creates a new Session attached to the Workspace.
- Workspace reassignment is available both through `open_workspace` and the Workspaces GUI. Sessions shows the current Workspace name/path read-only. Stored relative paths are resolved against `APP_DIR` only when an operation needs an absolute path.
- `open_workspace` checks only the selected Workspace root for guidance, in this priority order: `AGENTS.md`, `agents.md`, `CLAUDE.md`, `Claude.md`, `claude.md`. It returns the first matching absolute guidance path and never scans parent or child directories. It also returns `workspace_created` and a compact `memory_summary` with count/latest-key orientation for both selected Workspace and resulting Session; do not eagerly return memory values there.
- Tool/server descriptions must direct the agent to use the Workspace identity/guidance/Memory-summary fields returned directly by `open_workspace`, explicitly opt into creation only when desired, and read/follow `agent_guidance_path` when non-null. Published tool/input/output schema descriptions should be product-neutral; reserve the `MrMCP` name for actual server identity, branding, UI/resource identity, or behavior where the product name is semantically necessary.
- Changing a Session Workspace affects new calls immediately. Existing background and interactive processes continue with their original working directory.
- Disabling or deleting a Workspace moves associated Sessions to internal id `0` without terminating processes; such Sessions remain visible for operator reassignment but new Sessions cannot be opened into id `0` through `open_workspace`.
- Resolve the Session and Workspace once at the start of each call and use that fixed selection for the whole operation.

All relative paths and new child-process working directories must remain inside the selected Workspace.

JavaScript kernels are lazy and keyed internally by `(server_id, context_handle, root_id)`. Switching Workspaces selects or creates the matching kernel; switching back restores its previous state. Never share a kernel between different Sessions.

### UI design rationale and non-negotiable state model

The GUI uses one simple server-owned state machine. This rule exists because a previous unified-event refactor left sidebar clicks unable to change section: events were emitted, but there was no authoritative state transition and no guaranteed render path. Do not solve this class of problem with imperative DOM patches.

Every value that can change what the operator sees is graphical state and belongs to Deno, including apparently small values such as:

- the current sidebar section;
- which Tool-call or HTTP-log row is expanded;
- current filters, page number and page size;
- open/closed dialogs, confirmation targets and validation messages;
- form drafts, selected values, focus/selection metadata and per-section scroll positions;
- temporary outputs such as self-test results and live/reconnecting state.

Use stable identifiers for state that points at persistent data. An expanded row is stored as its database primary key, never as a row index, table position, DOM id derived from position or copied row object. This lets Eta reconstruct the same visible state after unrelated MCP, process or log activity.

The authoritative flow is always:

1. The WebView observes user activity and coalesces only noisy state updates before crossing the Tauri bridge: text `input` changes are debounced for 60 ms and merged by control id, scroll is debounced for 80 ms, and pending focus/scroll/input envelopes may collapse latest-wins in the WebView send queue. Click/action/change/blur/submit/navigation are semantic events: never debounce/drop them; flush pending text input first, then enqueue the semantic event in order.
2. Deno receives the already-coalesced envelopes and validates/processes every received event strictly sequentially. Do not add a second latest-wins/debounce/coalescing layer in Deno.
3. Deno updates `uiState` where required and performs database, filesystem, process, TLS, OAuth or command work.
4. Deno marks the UI dirty instead of rendering synchronously in the mutation path.
5. If the native window is hidden or minimized, stop there: retain only the dirty state while all authoritative Deno/DB/runtime state continues changing normally.
6. If the native window is visible and non-minimized, the render scheduler coalesces/throttles bursts and asynchronously builds the active view with Eta.
7. The backend Worker posts the completed HTML plus restoration metadata to the main thread, which emits it to the WebView over the Tauri event bus.
8. The WebView applies only the newest render revision through unmodified Morphlex with `preserveChanges: true`. Do not patch Morphlex or add form-state snapshots/replay/callback workarounds: use its built-in dirty-control semantics so user edits survive ordinary morphs while fresh server-rendered controls and later authoritative server changes can still establish values normally. Stable DOM ids should be used when stable node identity matters. A surviving enabled active form control keeps its native focus/selection; stale Deno focus metadata must not move its caret. Structural removal/replacement has normal browser effects. A hidden→visible transition forces one current full-state render; never replay intermediate hidden updates.

The same path applies to non-user events. A new MCP tool call, a log row, process output/completion, a Workspace change, OAuth mutation, certificate update or settings change must update backend state/data and enqueue the same render pipeline. There must not be a separate “automatic refresh” implementation.

Eta is responsible for conditional UI composition. It selects the visible section from `uiState.currentSection` with ordinary conditionals and renders only that section. Data access must be lazy and section-scoped: the projection or helper for Tool calls queries Tool-call data only while Tool calls is active; HTTP-debug data is queried only while HTTP debug is active; the same rule applies to every section. Do not preload every page merely because a full `#app` HTML fragment will be sent.

The WebView is deliberately not a second application runtime. It must not decide what section is active, toggle expanded rows locally, retain dialog state, fetch business data, or patch UI state with `classList`, `hidden`, injected rows or hand-built HTML. Apart from transport bookkeeping and applying Morphlex output, visible changes originate from Deno-rendered Eta HTML.

If a new interaction appears to require browser-local state, first add an explicit field to Deno `uiState` and route the interaction through the normalized input dispatcher. Exceptions require a concrete technical reason and must be documented here.

### Deno owns all ephemeral UI state

The WebView must not own an application-state object. Do not add `globalThis.mrmcpUiState`, browser-side section state, browser-side pagination state, browser-side expanded-row state or browser-side dialog state.

Deno owns one ephemeral `uiState` object containing at least:

- `currentSection` and per-section scroll positions;
- focus/selection metadata;
- the optional Sessions OAuth-client filter;
- command filters and pagination;
- guided-prompt filters, pagination and prompt drafts;
- Tool-call tool/command query, generic query, Session-PK/status filters, pagination, self-test output and expanded log primary key;
- HTTP-debug filters and expanded row primary key;
- Workspace, Command and Settings drafts plus inline field-validation state;
- active confirmation/form dialog and non-modal notice balloon.

Database primary keys identify expanded rows. Never use a row index or DOM position.

### Thin WebView transport

The embedded browser has only transport and DOM-application responsibilities:

1. delegate user events;
2. serialize them and emit them through Tauri `plugin:event|emit`;
3. receive render payloads through Tauri `plugin:event|listen` after the main thread sends them with `plugin:event|emit_to`;
4. morph the complete `#app` HTML using Morphlex;
5. apply scroll/focus metadata sent by Deno.

The browser must not call `/api/state`, `/api/render` or section-specific JSON endpoints. It must not execute database, filesystem, process, TLS, OAuth or command business logic. Local clipboard writes are allowed because they carry no persistent or graphical application state. Native drag `DataTransfer` may transiently carry only a numeric Session PK to a server-rendered Workspace drop target; it must not add/remove classes, move nodes, retain assignment state or otherwise alter visible UI locally.

### One backend input and render pipeline

WebView→backend delivery is ordered and source-coalesced in the WebView only. Text `input` events use a 60 ms debounce and merge by control id so the newest value for every changed control survives; scroll uses an 80 ms debounce; pending `inputs`, focus and scroll envelopes may replace an older pending envelope of the same type while still in the WebView send queue. Action/change/blur/submit/navigation and other semantic events are barriers: flush pending text input before them and never drop or reorder them. Deno must not coalesce again: it processes every envelope that crossed the bridge one at a time, in arrival order. The dispatcher updates `uiState`, performs the requested backend action and queues a render when required. Backend-originated changes from MCP calls, logs, managed processes, Workspaces, OAuth, TLS, settings and commands enter the same render pipeline through `emitUiChange`.

Rendering must not occur synchronously in mutation paths:

- use a short throttle to coalesce bursts;
- permit only one render at a time and assign every dirtying request a monotonically increasing render generation;
- if another event arrives during model/Eta construction, mark the current generation stale, abort cooperatively at the next async/yield boundary, discard the partial/intermediate HTML and restart exactly once from the newest generation; never finish or deliver intermediate renders when a newer state is already known;
- model building and every Eta fragment render must check the current generation before and after asynchronous work, so a burst does not repeatedly construct obsolete full HTML;
- yield before expensive work;
- gate the expensive path on native `visible && !minimized`; while false, retain `uiRenderQueued` only and do not call `buildUiRenderModel()`, Eta, HTML construction or Worker/WebView render delivery;
- if visibility becomes false during an already-started render, discard its finished payload and leave the queue dirty;
- when visibility becomes true, force one fresh complete render from the current Deno state regardless of how many hidden changes occurred;
- use Eta asynchronous rendering when available;
- send the completed full `#app` HTML through the Worker → main-thread → Tauri event path only while visible;
- main-thread→WebView render delivery is serialized with one in-flight payload plus one latest pending slot: while a render is in flight, replace the pending slot with the newest revision and skip every intermediate revision; the WebView also rejects any revision not newer than the last applied one.

Do not add interval polling, refresh timers, auto-refresh controls, manual refresh paths, hidden-render replay queues or multiple independent render queues.

### Selective rendering and data access

Eta selects the active section from Deno `uiState.currentSection`. `buildUiRenderModel()` may query only the current section’s data:

- Dashboard: endpoint summary and aggregates, Trash/Untrash activity, plus the compact active/recent Tool Call table. That table includes every in-flight Tool Call and calls completed within the last five seconds, using the same bounded tool/argument summary, Session id, elapsed time and persisted `progress_requested` marker. Keep a five-row minimum-height panel with no internal scrollbar; let it expand when more rows are simultaneously live/recent. Clicking a live/recent row sends only its stable log id to Deno; Deno clears Tool Call filters, selects the correct paginated log page, opens that exact detail row and supplies a one-shot `scroll_target` restoration hint so the browser only scrolls the already-rendered selected row into view. Deno schedules one-shot renders while calls are active and at completed-row TTL expiry; CSS may fade a completed row, but the browser must not own the timer/countdown or poll.

## Processes and PATH

The system-PATH setting is enabled by default.

- `exec` and `exec_start` must describe `args` as the exact ordered argv passed verbatim to the executable; agents should consult the command's `--help` rather than reinterpret uncertain option syntax.
- `exec` is foreground/request-scoped and retains the complete normalized combined stdout/stderr transcript until the call ends. Without `_meta.progressToken` it returns one final JSON result after process exit. With `_meta.progressToken` and SSE support it also emits incremental progress in 16 KiB/100 ms batches, then returns the same complete transcript in the final result. A client disconnect/cancellation terminates that child. Foreground custom commands use the same progress behavior.
- Persistent execution uses `exec_start`, `exec_attach`, `exec_write`, `exec_kill`, `exec_list` and `exec_status`. `exec_start` accepts no client-chosen process label. Its returned `exec_id` is exactly the numeric Tool Call log id allocated for that `exec_start`; it is monotonic/unique and every follow-up lookup is scoped by exact `(context_handle, exec_id)`. Keep the internal random `process_id` and OS PID only for database/GUI/diagnostics. `exec_start` starts immediately, retains the complete normalized stdout/stderr transcript, keeps stdin open, records client stdin writes internally and returns JSON without streaming.
- `exec_attach(exec_id)` consumes unread combined output through an internal cursor and exposes no public offset. With `_meta.progressToken`, emit all unread backlog through progress, continue emitting live output until the child exits/kills, then return the entire unread transcript covered by that attachment with `remaining_bytes: 0`. Without `_meta.progressToken`, return existing unread data immediately up to 16 KiB; otherwise long-poll until output arrives, then return once 16 KiB are available or 100 ms have elapsed after the first new data. `remaining_bytes` is the exact UTF-8 byte count already buffered after the returned chunk. Agents immediately call again while it is nonzero; with zero plus `status: running`, another call waits for future output/termination. Killing/failing while attached must wake the call and preserve the final available output/status. Only one attachment may be active per exec id. Disconnecting attach detaches only and never terminates the persistent child.
- `exec_write(exec_id)` writes/closes stdin and `exec_kill(exec_id)` terminates only persistent children in the same Session. `exec_list` exposes only currently running persistent executions for the exact `context_handle`; never include completed records there. `exec_status(exec_id)` is read-only/non-consuming and must work for running and retained completed/failed/timed-out/killed records, with `output=none|all|tail`, bounded `tail_lines`, and optional matching stdout/stderr selection through `separate_streams`. Completed in-memory records are retained by the existing 24-hour cleanup window and do not survive server restart. No MCP process input/result may expose internal `process_id` or OS PID.
- ON: prepend `.mrmcp/bin` to the supplied or inherited `PATH`.
- OFF: use only `.mrmcp/bin` in the child `PATH`.
- Use `ComSpec` on Windows and `SHELL` or `/bin/sh` on Unix.
- On Windows, spawn managed `exec` / `exec_start` children through `node:child_process.spawn` with `windowsHide: true` and adapt Node stdio streams to the existing Web Stream process pipeline. Do not regress to a spawn path that flashes a console window or steals WebView focus. Non-Windows managed processes may continue to use `Deno.Command`.
- Managed termination must use the runtime child-process `kill()` API directly. Do not spawn `taskkill`, `kill`, `pkill` or another platform helper and do not claim portable recursive process-tree termination: Deno/Node core provides no cross-platform tree-kill API. `SIGTERM` and `SIGKILL` remain distinct requests on Unix; on Windows Node may terminate the direct child without Unix signal semantics. Parent exit must still release a foreground MCP response after the bounded output-drain path even when descendants retain inherited handles.
- Explicit GUI/`exec_kill` termination uses `termination_source: "user"`; foreground request disconnect/cancellation uses `client`; timeout and server-shutdown requests use `timeout` and `server`, while an externally observable termination uses `external`. Keep `requested_signal` distinct from the actually observed `signal`; do not invent an observed signal when Windows reports none.
- Keep managed process access scoped to the exact `context_handle`; retain the Workspace and cwd snapshot captured at process start.
- `tools_log` is read-only and scoped to the exact `context_handle`. It returns only calls that reached MrMCP and excludes its own currently running log row. Keep `limit` bounded to 1–50 with default 10; `tool` and `status` are exact filters including `invalid`, `query` is a case-insensitive literal substring search across the complete stored log row, and `before_id` is the stable backward-pagination cursor. Filters are combinable. Use it to distinguish server-side execution/validation from upstream/client-wrapper rejection; never claim it can reveal a wrapper policy reason that was not sent to MrMCP.

## CDP browser control

The built-in CDP surface is deliberately low-level and dependency-free apart from optional lazy image conversion: exactly `cdp_call`, `cdp_subs` and `cdp_poll`. Do not import Puppeteer, Playwright, chrome-remote-interface or the reference `doc/CDP.js`; that file is design/behavioral know-how only. MrMCP speaks CDP directly over the browser-level WebSocket JSON-RPC transport.

- `browser` is a global persistent logical browser/profile label, not Session-owned state. On each `cdp_call` entry it is optional and defaults exactly to lowercase `main` when omitted. Validate the effective label as a safe directory component, store its profile at `APP_DIR/.mrmcp/cdp/<browser>/`, and persist one deterministic/probed unique loopback debugging port in `cdp_browsers`. The first CDP operation reconnects to an already-running browser on that port when possible; otherwise launch a CDP-compatible Chromium browser automatically with the persisted user-data-dir and port. `MRMCP_CDP_BROWSER` may override executable discovery. Spawn the GUI browser detached/unref'd with ignored stdio so it can outlive MrMCP; shutdown closes only MrMCP's WebSockets and never terminates the browser process.
- Preserve the operational launch tuning extracted from `doc/CDP.js`: browser profile/debugging setup plus background-networking/timer/renderer tuning, back-forward-cache, component/default-app/update behavior, first-run, color-profile, metrics, keychain/password-store, service autorun, tagged-PDF and search-choice tuning are deliberate. Keep the launch list explicit and synchronized with the implemented CDP lifecycle rather than replacing it with a third-party browser launcher.
- `target` on `cdp_call` is an optional persistent logical **page** label. Persist only `(browser,target)->targetId` in `cdp_targets`; never persist `sessionId`. If the saved targetId is still a live `page`, reuse it. If it disappeared because the page/browser was closed, lazily `Target.createTarget({url:"about:blank",background:true})`, replace the saved targetId and continue. Omit target for browser-level standard commands; `_mrmcp` page operations require target. Chrome/CDP live state is authoritative; the DB is only memory of logical identity.
- One browser WebSocket uses flattened sessions. Maintain runtime-only `targetId -> sessionId` and reverse maps from `Target.attachedToTarget`; invalidate on `Target.detachedFromTarget`, `Target.targetDestroyed`, target crash or WebSocket close. After MrMCP reconnects while the browser remains alive, recover the logical target from its persisted targetId and obtain a fresh session with `Target.attachToTarget({targetId,flatten:true})` as needed. Never require or accept agent-supplied `sessionId` or JSON-RPC `id`; MrMCP owns both transport fields.
- Initialize browser connections with `Target.setAutoAttach({autoAttach:true,flatten:true,waitForDebuggerOnStart:true})`, `Target.setDiscoverTargets({discover:true})` and `Target.getTargets()`. New page targets therefore arrive paused. While the page is still paused, initialize its session with `Runtime.enable`, `Page.enable`, `Network.enable`, best-effort `ServiceWorker.enable`, `Emulation.setFocusEmulationEnabled({enabled:true})`, `Runtime.addBinding({name:"_send_to_cdp"})`, and best-effort push-messaging `BackgroundService` clear/start-recording calls. Then issue `Runtime.disable` **before** `Runtime.runIfWaitingForDebugger`. `Runtime.disable` disables execution-context reporting; it does not remove the binding or prevent later raw `Runtime.evaluate` calls. The `_send_to_cdp(string)` binding remains the page-to-CDP notification bridge through `Runtime.bindingCalled`. Non-page auto-attached targets must be resumed rather than left paused. Keep initialization best-effort across optional domains and expose setup errors diagnostically.
- `cdp_call` is **always batched**: `calls[]` is required even for one request, accepts 1–100 entries, and a single batch may span browsers and targets. Each entry's `call` contains exactly one of standard `method` or private `_mrmcp`. Standard `{method,params}` is transported untouched except for server-owned id/session routing. `_mrmcp` currently supports only `click` and `find`, internally translated to `Runtime.evaluate` while exposing logical method names `_mrmcp.click` / `_mrmcp.find` in retained response metadata. Preserve the reference augmented XPath rewrites: `ends-with(a,b)` -> XPath-1.0 `substring(...) = b`, `icontains(a,b)` -> case-insensitive `contains(translate(...),b)`. `click` preserves the reference `awaitPromise`, `returnByValue`, `silent`, `userGesture`, retry count and interval semantics; `find` returns bounded compact node/element text/attributes/rect metadata. Do not add separate MCP tools `cdp_click`/`cdp_find`.
- `wait` is one batch-wide flag: `wait=true` dispatches every entry and waits independently for every response; `wait=false` returns assigned ids immediately while preserving eventual responses for `cdp_poll`. Preserve input order exactly and represent preparation/protocol/transport failures per entry without aborting siblings. Raw CDP errors remain visible in returned/polled `cdp`. Never accept agent-supplied JSON-RPC ids or sessionIds.
- Standard `Page.captureScreenshot` returns Base64 in CDP `result.data` and does **not** imply disk persistence. Optional per-entry `_image` is MrMCP response metadata/post-processing, never part of raw CDP params and valid only for `Page.captureScreenshot` with `wait=true`. `_image.return` is `base64`; `format=original` preserves browser bytes without loading an image codec. `format=webp` lazily uses public `auto.vips.decodeImage` / `auto.vips.encodeImage`, optionally resizes by positive `scale`, uses the current fixed WebP Q=80, replaces only returned `cdp.result.data`, and adds compact `image` metadata. Never import Sharp directly from MrMCP or reach into Auto.js internal module paths. Every standard screenshot request parameter remains available unchanged to the agent.
- `cdp_subs` is the single global runtime subscription mutator, never Session-owned or persisted. It requires one `browser`, applies removals before additions, and accepts `add`/`remove` in the same call. `add="*"` creates one catch-all subscription; `remove="*"` removes every live subscription for that browser. Subscription specs may filter logical `targets[]` (including `*`), exact `methods[]`, `method_prefixes[]` (both supporting `*`), optional browser-level traffic, and optional regex source/flags. Regex is evaluated against `JSON.stringify` of the complete raw inbound CDP message, not only its method. Target/method/regex dimensions combine with AND; exact+prefix alternatives combine with OR. Internal target/session bookkeeping always processes required `Target.*` events regardless of public recording filters. Notifications enter the public recorder only when at least one live subscription matches; responses are retained independently.
- Keep one bounded per-browser ring, not one copy per subscription. The cap is both message count and serialized bytes. Each subscription owns only filters plus an ascending cursor; `cdp_poll(subscription=...)` advances that cursor by default and reports exact ring-loss plus stream-reset diagnostics. Ad-hoc `cdp_poll(browser=...)` has no cursor and returns the latest N matching retained messages from the tail in chronological order. Method filtering applies to notification method names and remembered standard/private logical request methods of responses. Oversized messages that exceed the byte cap are dropped rather than partially rewriting raw CDP payloads.
- Navigation, arbitrary evaluation, screenshots, cookies, DOM, input, target/browser domains and every other protocol operation remain standard `cdp_call` methods. Do not add `cdp_launch`, `cdp_eval`, `cdp_navigate`, `cdp_screenshot`, standalone subscription/unsubscription tools, or other convenience MCP surfaces unless deliberately revisited.

## Persistent memory

The public memory surface is exactly `memory_find` and `memory_set`; do not add a separate `memory_get`, hidden model memory, implicit current-Workspace lookup, or another memory store. Exact lookup is `memory_find` with `key`.

- Every call explicitly requires `scope=session|workspace`. Session scope always means the exact current `context_handle`'s numeric Session id and rejects a Workspace argument. Workspace scope always requires an explicit registered Workspace label, resolves it to the Workspace id, and is shared across Sessions independently of the caller's currently selected Workspace.
- Keep one SQLite `memories` table with unique `(scope,owner_id,key)`, stored value text, explicit `is_json`, TTL seconds, `set_at` and `expires_at`. `memory_set` requires explicit `json=true|false` whenever setting: true must parse as valid JSON before storage, false stays ordinary text. Values are limited to 1 MiB. `ttl_seconds=0` is permanent; positive TTL starts from each set/replacement. Lazily purge expired rows before tool finds/sets and before GUI projection rather than running a background expiry poll.
- `memory_set` sets/replaces a key or deletes it with `delete=true`; delete excludes both value and json. Replacement intentionally gets a fresh row id and `set_at`. Never search another Session's memory through the tool: Session scope is capability-scoped to the supplied current handle.

Workspace rename updates the stored display label while owner id remains authoritative. **Clear Operational Data preserves all live Memory rows** along with Sessions, Workspaces and CDP browser state.
- The desktop **Memory** section is lazy and uses the same table. It filters by scope, Session, Workspace, set-date range and text, paginates 25 rows/page, shows JSON/TEXT plus set/expiry/TTL and a compact value preview, and exposes New Memory, managed View/Edit and confirmed Delete actions. ## Published content and MCP App widget

`publish` is the single supported user-publication surface. Keep the contract stateless across Tool Calls and deliberately source-oriented:

- every call supplies exactly one of `path`, `text` or `base64`, plus required `mime_type`; never add a transient `image_id`/previous-result lookup or another cross-call cache. `path` snapshots an existing regular Workspace file, `text` is encoded as UTF-8 bytes, and `base64` is decoded directly. `filename` is optional; path defaults to its source basename while direct content gets a MIME-based fallback name. `title`, `description` and `height` are presentation metadata. `presentation=auto|inline|download` is only a smart-widget hint and must never override the actual MIME-driven HTTP delivery semantics;
- all three source forms enter the same serialized publication chain and end as ordinary physical files under `.mrmcp/publish/`, named with the random public capability id prefix plus a sanitized presented filename. Do not store HTML/text/Base64 payloads inline in SQLite or maintain a separate HTML persistence path. File-origin publications retain their source path/name metadata; direct text/Base64 publications have no source path. Publications remain immutable snapshots after creation and survive source changes/moves/deletion and backend restarts until explicit Published Delete, Published Clear Matching or Clear Operational Data removes them;
- use one fast deterministic `content_key` algorithm for every source: SHA-256 over size plus first 10 bytes, last 10 bytes and central 10 bytes. Never hash a whole large file merely for deduplication. The random `published.id` remains the persistent public capability and must not be replaced by the content key. Equal non-empty content keys within a server reuse one physical snapshot. `published_uses` remains a relationship table with at most one current relation per published item + Session + call-time Workspace; repeat publication in the same relation updates source/display/MIME/title/description/presentation/height metadata and timestamp, while another Workspace gets a distinct relation without another payload copy;
- the public content capability URL is `/published/<id>/<filename>`. The filename suffix is presentational: a valid id remains sufficient to address the resource and a matching relation may provide its current filename/MIME metadata. Always include the sanitized filename in `Content-Disposition`. Browser-displayable MIME types use `inline`; opaque/binary/executable MIME types use `attachment`. The agent's `presentation` hint affects only the widget, never these response semantics. The returned `structuredContent.uri` is this actual content URL, not the MCP App resource URL;
- `publish` has one versioned `PUBLISH_UI_URI` View and attaches it only through `_meta.ui.resourceUri`; do not add legacy OpenAI Apps metadata such as `openai/outputTemplate` or `openai/toolInvocation/*`. Externally returned `tools/list` and `resources/list` entries use fresh random `?instance=...` suffixes for host cache busting, and each successful `publish` result may carry its own fresh View URI hint. `resources/read` accepts the canonical URI or an instance URI, echoes the exact requested URI, and resolves by `params.uri` without requiring contextual `Mcp-Name` equality;
- the smart widget reads only its standard `ui/notifications/tool-result` payload and `structuredContent.uri`. Never use MCP `resource_link`, `openai:set_globals`, `window.openai.toolOutput`, inline Base64/data URLs or another global tool-output compatibility path. Each mounted View pins the first valid publication `id` and ignores later different ids; missing initial output is pending, not an error. If `ui/initialize` times out, still emit `ui/notifications/initialized` and remain ready for a later tool-result notification. Start JSON-RPC request ids from a randomized positive base;
- the widget renders `title`, `description` and a compact metadata line (presented filename, MIME, byte size and current call source `path|text|base64`) above the published element. When the main presentation is an inline image/iframe preview, expose **Open original** immediately below that metadata and open the persistent content URL in a new window/tab. Do not show a redundant header action when presentation falls back to the file card, because that card's **Open File** action is already the primary content link. In `auto`, ordinary image MIME types use `<img>`, browser-previewable text/JSON/XML/PDF/media/HTML-like content uses an iframe preview where appropriate, and opaque types use the file card. `inline` asks for the preview path when supported and falls back safely when unsupported; `download` selects the file card. Preview/open actions always target the persistent content URL itself. HTML and other iframe content must remain nested and sandboxed; allow scripts/forms/modals/popups when needed but never `allow-same-origin`. Do not impose the restrictive active-document CSP on published HTML/XHTML itself, because the nested iframe sandbox is the isolation boundary. Self-contained HTML/CSS/JavaScript is the portable default; external resources/network calls remain host/browser/CSP/CORS dependent and the descriptor must say so;
- do not add `exec.return_files*` shortcuts. A command that creates a file is followed explicitly by `publish(path:...)`; direct small generated content may instead use `text` or `base64`. The normal MCP request-body limit bounds `text`/`base64` inputs.

The local administration GUI has one **Published** section backed by `published`, `published_uses` and `.mrmcp/publish/`. Query it lazily only while that section is active. One row represents one deduplicated content resource and shows creation time, random publication id, deterministic content key, MIME type, physical `published_name`, presented filename, optional title/presentation, per-resource HTTP request count/last request, size and every publication reference. Each reference uses the call-time numeric Session id plus call-time Workspace/source/display metadata from `published_uses`; never derive historical Workspace display from the Session's later current Workspace. Session filtering must match any attached reference. Keep Session and size filters, pagination and Clear Filters; there is no file-vs-HTML type filter. Clicking the physical published filename sends only its computed public HTTPS content URL from the backend Worker to the Tauriless main thread, which opens it with Tauri Opener `plugin:opener|open_url`; the WebView must not perform native filesystem opening itself. Per-row Delete removes one resource; confirmed **Clear Matching** removes every resource matching the current filters across all pages, including every reference and physical snapshot. Clear Matching uses the Tool Call maintenance barrier so an in-flight publish cannot race cleanup. Do not add global Published/template-load counters or widget diagnostic fetches. Widget CSP declares only the resource/frame domains actually needed, and every template behavior change bumps its versioned `ui://` URI.

## Filesystem tools

The built-in filesystem surface is deliberately small and uniform:

- discovery/read: `fs_glob`, `fs_grep`, `fs_read`, `fs_navigate`, `fs_stat`;
- content mutation: `fs_write`, `fs_edit`;
- structural mutation: `fs_mkdir`, `fs_copy`, `fs_move`, `fs_trash`, `fs_restore`.

Do not reintroduce separate single-file/batch variants, a generic `replace` tool, permanent delete, filesystem transaction handles or server-side pagination/navigation state. Prefer these tools over shell commands, `uv`, Python or `js` whenever they express the operation directly. `TOOLS.md` is the human-readable contract and rationale for the published tool surface; keep it synchronized with descriptors and implementation behavior.

All filesystem navigation/search pagination is stateless. `fs_glob` orders paths deterministically and resumes with the explicit `after_path` returned as `next_after_path`. `fs_grep` resumes with explicit `{path,line}` `resume_after` / `next_resume_after`. `fs_navigate` receives the current line and direction for every file on every call. Never retain hidden server cursors for these tools.

`fs_glob`, `fs_grep` and `fs_trash.selection` share one path-selection model: `path`, globstar `include[]`, globstar `exclude[]`, `gitignore` and `hidden`. `gitignore=true` applies applicable parent `.gitignore` rules and nested `.gitignore` files encountered while descending; do not imply support for Git's index, global excludes or `.git/info/exclude`. Do not add a separate recursive-gitignore switch or dependency-specific traversal policy such as `include_dependencies`.

Use explicit names that remain understandable in Tool Call logs. Text context counts are `context_lines_before` / `context_lines_after`, never generic `before` / `after`. Pagination fields identify what they resume (`after_path`, `resume_after`). Trash identifiers are `trash_id`, never generic `action_id`.

Support explicit UTF-8, UTF-16LE, UTF-16BE, Windows-1252 and Latin-1 directly in the ordinary text tools, including BOM and `LF`/`CRLF`/`CR` controls. Keep logical text separate from physical representation. The architectural goal is to minimize representation burden on the agent: infer/preserve every byte-level choice that is unambiguous from the source, normalize harmless differences in agent payloads, and require an explicit agent choice only for genuine ambiguity. Do not trade this convenience for permissiveness: malformed input, unsupported text and non-lossless conversions must fail rather than be guessed, substituted or silently repaired. `auto` decoding must pass the complete original byte buffer to pinned `chardet` and use only its detected charset; do not override it with BOM, UTF-8-validity, UTF-16 structure or any other charset heuristic, and fail automatic decoding if the detector returns no charset. Explicit input encodings must bypass `chardet` rather than running detection and discarding its answer. Physical BOM detection remains MrMCP-owned and independent strictly to report factual recognized prefix bytes; never use it for charset selection and never infer it from the selected encoding. Decoder handling of a matching BOM is charset decoding semantics, not detection: custom Unicode decoders must match native `TextDecoder` behavior and consume an initial U+FEFF BOM. Native `TextDecoder` paths stay fatal on malformed input; never fall back to a permissive decoder merely because fatal decoding rejected invalid bytes. Charset-only `iconv-lite` fallback must prove lossless decode/re-encode byte identity before accepting input. Writes must likewise prove that final bytes decode through MrMCP's own path to exactly the requested text, and that requested physical BOM presence/absence matches the bytes, so unsupported characters or malformed Unicode never silently become `?`/replacement characters. Preserve a detected ASCII result as strict ASCII rather than converting it to UTF-8 or relying on the WHATWG `ascii` alias. Do not persist an out-of-band "intended encoding" for ambiguous byte streams: a new UTF-8 file containing only ASCII-compatible bytes may later auto-detect as ASCII, and the pinned detector remains authoritative. Treat BOM as a physical prefix invariant even for explicitly selected legacy encodings: `add` requires a BOM-capable Unicode encoding, but `preserve` on legacy text may succeed naturally when the encoded text itself reproduces the original recognized prefix; never prepend an extra Unicode BOM to legacy payloads. `output_encoding:"preserve"` reuses the detected source charset and defaults to UTF-8 only for a new file; `bom:"preserve"` preserves physical BOM presence and defaults absent only for a new file. `fs_write` must not decode an existing source gratuitously: require decoded source metadata only when preserving its charset, or when preserving line endings and the replacement actually contains breaks; raw BOM presence can be inspected without decoding. Fully explicit whole-file replacement must therefore remain possible even when old bytes are not decodable as text. Reads/searches normalize returned text to LF, never invent a trailing empty line solely because the file ends in a newline, and report empty files as zero text lines. Byte-bounded `fs_read` must prioritize the requested range over optional context: fill the budget with requested lines first, use only remaining space for `context_lines_before` / `context_lines_after`, and paginate only when the requested range itself is incomplete. Context must never displace requested content or cause `next_start_line` to repeat indefinitely; every continuation must advance beyond the requested start. Report `line_endings:"none"` for any text with no CR/LF separator, including both empty and non-empty single-line files. Incoming LF/CRLF/CR or mixed breaks from agent text are logical content only: do not reject them just for differing from the target style, because explicit `line_endings` must normalize all breaks and `preserve` must normalize them to an existing uniform source style. If the resulting text has breaks but preservation has no unambiguous source style, return `mixed_line_endings` for a mixed source or `line_endings_required` for a new/none source and require explicit `lf`, `crlf`, or `cr`. If the resulting text has no breaks, allow `preserve` even for mixed/new/none because the output style is unambiguously `none`. Tool string arguments are already JSON-decoded text: never apply a second C/JavaScript-style escape-decoding pass.

Every tool that reads regular-file content for `fs_read`, a matched `fs_grep` file or `fs_navigate` returns an opaque whole-file `fingerprint`; `fs_stat` may compute one when explicitly requested. Mutation tools accept `expected_fingerprint` per file and return a structured `fingerprint_mismatch` result instead of writing when the current bytes differ. Treat the fingerprint as an opaque concurrency token, not as a public SHA-256 contract even if SHA-256 is the current implementation.

Batch filesystem entries are independent. Do not expose `atomic`, do not roll back successful earlier batch entries because a later entry fails, and do not pretend filesystem operations form an OS transaction. Return structured per-entry status plus `succeeded`/`failed` counts so the agent can see exactly what happened. A single recursive copy/move/trash/restore may report `failed_partial` when the destination/payload exists after failure; leave that state visible rather than attempting a second best-effort rollback operation. Recursive copy and the cross-filesystem move fallback must preserve symlinks as links rather than dereferencing them.

`fs_edit` is the important local exception: each file is internally all-or-nothing at the edit-validation level. Read the file once, verify `expected_fingerprint` against that initial version, normalize the in-memory edit representation consistently, apply its `edits[]` sequentially to the evolving document so edit N sees edits 1..N-1, validate every `expected_occurrences`, and only then write that file once. If any edit validation fails, do not write that file; continue independently with other files. Duplicate file entries are invalid. Successful results report compact ordered `{index, expected_occurrences, occurrences}` metadata without echoing potentially large `old_text`/`new_text` values.

Filesystem removal is trash-only. There is exactly one MrMCP metadata directory, `APP_DIR/.mrmcp`; named Workspaces never receive a `.mrmcp` directory from MrMCP. `fs_trash` accepts explicit paths and/or one structured selection, collapses nested selected targets, and stores successful payloads from every Workspace under the single `APP_DIR/.mrmcp/trash/<trash_id>/` directory with sibling `<trash_id>.json`. `trash_id` values are globally unique in that store and use local date/time to the second with a numeric suffix only on collision. Write the manifest before moving payloads so original absolute paths and deterministic payload names are recoverable even when later entries fail. `fs_restore` is Workspace-scoped, restores available payloads independently, leaves failed payloads in the trash for retry, and removes the transaction only when no payload remains. Exclude only the real `APP_DIR/.mrmcp` metadata directory from trash targets/selections; a same-named directory inside an unrelated Workspace is not MrMCP metadata. `fs_trash` and `fs_restore` are intentionally non-destructive in MCP annotations; Dashboard Trash/Untrash activity uses the single global trash store plus completed Tool Call logs.
