# MrMCP implementation guide

## Current release and files

MrMCP 0.11.4 consists of thirteen root project files, a Bun dependency manifest/lockfile, build/check scripts, one GitHub Actions workflow and one versioned asset directory:

- `mrmcp.js` — Bun backend, MCP `2026-07-28`, OAuth/Basic authentication, Turso, native GPUIX UI and desktop launcher.
- `mcp.yaml` — separate authoritative stdio MCP server catalog, managed by the MCP Servers page. Embed/materialize it once beside the other catalogs without overwriting edits; binaries live in `.mrmcp/mcp/bin`, outside Commands discovery.
- `commands.yaml` — versioned editable extra-command catalog; keep it in the repository root, never under `assets/`.
- `guided_prompts.yaml` — versioned editable MCP guided-prompt catalog; keep it in the repository root, never under `assets/`.
- `proxies.yaml` — authoritative proxy pool/source/cooldown configuration; Settings → Proxies edits it, while proxy outcome statistics live in Turso. Embed it as a first-run template and preserve user edits.
- `search.yaml` — authoritative Search/OCR and embedding configuration, edited by Settings → Search; embed as a first-run template beside the other YAML catalogs and never overwrite user edits.
- `README.md` — concise current user/operator behavior only; keep release history out of it.
- `CHANGELOG.md` — release history only.
- `AGENTS.md` — implementation invariants and release checks.
- `TOOLS.md` — current built-in tool contracts, arguments, semantics and design rationale.
- `LICENSE` — sole project license file: MIT for MrMCP plus the complete JSONEditor Apache-2.0 notice/text. Embed it in every standalone build; preserve dependency-owned licenses in their packages.
- `.github/workflows/release.yml` — tag-driven native builds with Bun 1.4.4. Verify VERSION == tag; build Windows x64, Linux x64 and macOS Apple Silicon desktop. Publish their exact three assets, with an ad-hoc signed app/DMG on Apple Silicon. Never add extra checksum/tar/zip release assets.
- `package.json`, `bun.lock` — Bun dependency metadata and reproducible installation.
- `.github/build.mjs`, `.github/check.mjs` — target packaging and integration verification.
- `assets/` — branding/build assets plus historical vendor files, including `morphlex.js`, vendored `jsoneditor/` (minimalist JS/CSS/icon; license retained in root `LICENSE`), `mrmcp-logo.svg`, `mrmcp-logo.png`, `mrmcp.ico` and the numbered administration screenshots; do not duplicate them in the repository root.

The only public MCP protocol endpoint is `/mcp`. The public HTTPS listener also serves the read-only unauthenticated `/mrmcp-icon.png` branding asset referenced by MCP `serverInfo.icons`. The administration UI is native GPUIX and opens no GUI network listener.

OAuth DCR client registrations remain persisted until explicit deletion; routine maintenance expires codes/access tokens but never expires registrations based on age or current token presence. ChatGPT recovery after an absent cached registration is restricted to exact HTTPS origin `https://chatgpt.com`, without credentials/query/fragment, and either `/connector/oauth/<callback_id>` or `/connector_platform_oauth_redirect`. Recover only after ordinary resource/scope/PKCE S256 validation, require fresh consent, preserve exact callback binding during code exchange and return the advertised issuer as `iss`. Do not treat other ChatGPT paths or lookalike origins as recovery callbacks.

## Desktop shell

Keep hand-maintained source readable even when reducing its size: use ordinary multiline formatting, one clear operation per line and a roughly 100–120-column guideline. Apply this to schemas, scripts and embedded JavaScript, JSX and text templates too. Reduce code through structure and reuse, never source minification or monoline packing; formatting may increase bytes. Preserve literal output and protocol contracts when wrapping embedded content. Build-time minification of generated executables remains separate from source style.

Bun owns application execution, HTTP/TLS and backend logic in the same event loop as the native GUI; GPUIX owns native rendering. Use the public npm packages from package.json with bun.lock for reproducibility. Auto.js and CDP.js use their unversioned public entrypoints with latest update policy. Do not import private Auto.js vips.js or Sharp, patch vendor libraries, write another FFI wrapper, create a Rust/Tauri scaffold or introduce another GUI framework. Use the official @gpuix/react renderer with React for native reconciliation; do not maintain a second application reconciler.

The only application CLI modes remain desktop, --backend and --add-workspace <name> <path>. Build/check scripts under .github are development tooling. Headless mode must never load GPUIX, construct UI projections, send native notifications or read GUI-only assets. The one-shot Workspace path validates/inserts and closes Turso before listener/TLS/browser or GUI startup (the public Turso native package may require software-cache extraction). Inspect schema compatibility before application cleanup or editable sidecar materialization; preserve schema 6 and the recreate-only recovery gate.

Desktop mode is one Bun process/event loop. GPUIX initializes before starting the backend directly on the same thread; keep native frame callbacks bounded and let the public runtime pace them, including the macOS display link. There is no backend Worker, Worker message bus, serialization or render-tree copy. NativeUiHost exposes completed backend projections through React useSyncExternalStore. Native intents call the backend directly; independent asynchronous actions remain concurrent. There is no global GUI input queue or transport sequence/acknowledgment protocol. Initialize one window, preserve schema recovery in that window and close the backend gracefully before explicit process exit. Headless and one-shot modes never load GPUIX. Kernel Workers belonging to the explicit js tool remain independent and are not a background backend.

GPUIX owns native painting/window integration; application backend and GUI share the Bun event loop. Document OCR defaults to Rag/Xberg PaddleOCR, avoiding OS COM OCR initialization on this path. The optional native provider and Auto.js AAF scenarios retain their public API. Verify Windows OCR in the actual GUI-first initialization order; do not restore a backend Worker solely for this purpose. Keep expensive synchronous JavaScript work bounded/yielding; asynchronous database APIs do not imply every native CPU operation runs in parallel.

GPUIX 0.11.0 has no public tray, OS notifications, hide-on-close, custom native window-icon setter or reliable minimized/visible event. Tray and OS notification delivery are suspended; retain their saved per-type preferences and show the limitation beside disabled controls. Do not build discarded notification payloads or issue notification-only queries while this capability is unavailable; keep the notification contract below for reactivation. Do not create a fake tray, use another shell/library, add a custom native bridge or silently claim those integrations work. Windows executable branding and macOS app-bundle icons remain enabled. Directory drops add enabled Workspaces using existing deduplication/unique-name rules; Session-to-Workspace drag/drop uses transient numeric Session identity and backend assignment. Windows x64, Linux x64 and macOS Apple Silicon have a native GUI. macOS Intel is not supported. Build Windows on Windows so both --windows-hide-console and --windows-icon work; build other targets on matching native runners. Keep native package binaries only for the target. Document retrieval uses rag.js with Turso and its native Xberg CPU/ONNX dependency.

## Database: direct current schema with a recreate-only version gate

The main store uses the existing public @tursodatabase/database 0.8.3 async driver, schema 6. Every statement is awaited, with its own prepared handle; never share a bound statement between concurrent calls. withDbTransaction owns the public transactionAsync handle through AsyncLocalStorage so all nested SQL uses that handle and unrelated requests wait outside the transaction. Discard completed handles in deferred work; schedule GUI projections after transaction completion. Authorization-code consumption, refresh issuance and proxy reservations/reports are atomic. Reserve Tool Call controls before asynchronous Session resolution so maintenance drains initialization too. Turso native FTS indices replace FTS5 for both Disk and TEMP Memory logs; preserve search, volatility, cleanup/VACUUM and monotonic IDs. Read schema version before any application-side mutation; archive incompatible data only after explicit Start Fresh. The engine exclusively locks the main database across processes; report that another instance owns the directory rather than bypassing that lock.

The repository is in development. There is no backward-compatibility or migration layer. `schema_meta(id=1,version)` plus `DB_SCHEMA_VERSION` is only a fail-fast recreate boundary for the exact current schema.

1. Use only `schema_meta(id=1,version)` / `DB_SCHEMA_VERSION` for schema compatibility detection. Do not add `PRAGMA user_version`, migration tables or a second version mechanism.
2. Prefer extending an existing logical table over creating auxiliary tables whose only purpose is compatibility or carrying fields that naturally belong on that table. Do not create a separate compatibility table when adding fields to the existing current-schema table is simpler. Ensure genuinely distinct current tables/indexes directly at startup with `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`.
3. Do not add schema migrations, compatibility backfills or startup ALTER TABLE mutations. Inspect the existing .mrmcp/mrmcp.sqlite before normal startup, temporary-file cleanup or editable sidecar materialization. An unversioned or differently versioned database opens the local native recovery confirmation with the absolute data directory and proposed sibling .mrmcp.backup-YYYYMMDD-HHmmss path. Only Start Fresh renames the entire old directory, including Turso WAL and all state, without replacing any existing backup. Quit preserves it. Never import old data or silently delete/reset the database. Reuse the native window when continuing after recovery. Headless/one-shot modes require interactive terminal confirmation; unattended input fails with recovery instructions and never loads GUI assets.
4. The schema-version check is fail-fast validation, never a migration framework. Keep the clean current schema authoritative and remove obsolete tables/columns rather than retaining compatibility shapes.
5. Never import legacy configuration keys or identifiers.
6. Never retain an old table or column only for compatibility.
7. Never accept legacy `opaque_` values, `server_opaque` arguments or transport-derived session identifiers.
8. A clean schema must create no named `default` Workspace and `roots.name` must be globally unique with `UNIQUE(name)`, never `UNIQUE(server_id,name)`.
9. `contexts.id` is the numeric administrative Session primary key; `contexts.handle` remains the unique opaque Session bearer capability. Tool Call and process-history rows retain both `context_id` and internal `context_handle` snapshots. `logs.progress_requested` is transport metadata stored directly on the Tool Call row and never injected into tool arguments. Every Tool Call receives one stable integer id before execution; `exec_start` returns that same Tool Call id as public `exec_id` regardless of whether history storage is Disk or Memory. Disk rows live in the main database; Memory rows live only in Turso TEMP structures and disappear on restart. `process_runs` is always a main-database process-subsystem table independent of Tool Call Disk/Memory storage; `process_runs.log_id` is only a correlation to the originating Tool Call id and may outlive that Tool Call history row. HTTP diagnostic rows keep their historical Session/Workspace association in additive `debug_log_workspaces(debug_log_id PRIMARY KEY, context_id, root_id, root_name, root_path)` with `ON DELETE CASCADE`; the HTTP Log must never derive a historical Workspace label from the Session's later current `root_id`. Context rows may retain observational creation-client metadata (auth kind, OAuth client id/name and User-Agent); that metadata never owns or authorizes the Session. Tool Call ids must never be reset or reused.
10. Settings **Clear Operational Data** is a history/data cleanup, not a configuration reset: preserve `proxy_stats`, `config`, `server_config`, `custom_tools`, all OAuth tables, `roots`, `contexts`, `memories`, `subagents`, `subagent_messages`, `cdp_browsers`, `cdp_targets`, `trash_transactions`, `trash_items` and the persistent `.mrmcp/cdp/` browser profiles; clear both Disk and Memory Tool Call history plus FTS/descriptors, completed/orphaned process-history records while preserving active process rows/runtime, HTTP log rows plus Workspace snapshots, every row in shared `published` plus its `.mrmcp/publish/` payload snapshots, and reset metrics. After the main-database deletion transaction commits, run `VACUUM` followed by `PRAGMA wal_checkpoint(TRUNCATE)` so freed Turso pages and WAL storage are returned to disk. Reset the `debug_logs` sequence only; never reset Tool Call ids. Page-level confirmed Clear actions remain required: Tool Calls clears both history tiers without stopping already-detached persistent processes; Sessions deletes every Session after draining in-flight Tool Calls and requests termination of running persistent processes owned by those Sessions while preserving Tool Call history snapshots; Workspaces deletes every named Workspace and moves Sessions to root id `0` without touching files or running processes; OAuth Clients removes all OAuth clients/codes/access/refresh tokens while preserving Sessions and Basic authentication; HTTP Log clears HTTP rows plus `debug_log_workspaces`. Dashboard **Empty Trash** permanently removes the contents of the single `APP_DIR/.mrmcp/trash` store plus `trash_transactions` / `trash_items` metadata. Tool-Call-dependent maintenance uses one Promise barrier rather than an application queue: new Tool Calls wait, already in-flight Tool Calls finish, maintenance runs, then waiting Tool Calls continue. Maintenance dialogs are confirmation-only and long-running maintenance reports completion/failure through the backend-owned notice balloon. Dashboard always exposes `activeCallControls.size` as Tool Calls In Flight. Clear Operational Data must not delete certificates, command files/catalog data, trash contents or Workspace files outside dedicated publish snapshots.
11. Tool Call history has two independent operator policies. **Storage** is `disk` or `memory`: Disk survives restart in the main Turso database; Memory uses Turso TEMP tables/FTS on the same connection and is volatile. **Payload retention** is `payload` or `metadata`: Payload stores exactly one canonical serialized MCP JSON-RPC request packet and one canonical serialized MCP JSON-RPC response packet; Metadata keeps identity/Session/Workspace/status/timing/progress plus bounded errors but stores neither packet. Do not persist secondary Tool Call copies of arguments, structured returns, stdout/stderr, MCP transport additions or extracted binary payloads. Binary/image/text interpretation for debugging is derived from the canonical packets only when a Tool Call detail is viewed. Historical tool descriptors remain separate deduplicated schema snapshots because they describe the tool contract seen by that call rather than duplicate its transport payload. Payload policy is observability only: it must never remove state required for a feature. Persistent-process command/output state, Browser rings, Memory, Published data, CDP state and other functional subsystems retain whatever they need independently of Tool Call payload mode. GUI/tools must inspect each row's actual capabilities (storage/payload/field presence), not branch on the current global setting except in Settings itself. Disk retention uses `tool_call_retention_hours` (`0` = indefinite); Memory retention uses `tool_call_memory_retention_minutes` (default 60, `0` = until restart). Retention removes only completed eligible Tool Call history in its own tier and never deletes process/CDP or other functional subsystem state. Routine retention must never VACUUM. Keep configuration/server/tool descriptors cached coherently, derive Session statistics with indexed aggregate queries instead of a mutable Session-stats cache, use bounded Turso busy timeout and prepared-statement cache, batch low-value request metrics, and index canonical packets asynchronously through contentless FTS5 without duplicating source text. Database mutation effects must be explicit at semantic operation boundaries: never regex-parse SQL text to infer cache invalidation or GUI render scopes. `structuredContent` is the canonical structured MCP result; the required text content for structured tools must stay concise rather than pretty-printing another complete JSON copy. Normal Tool Calls remain concurrent except for the maintenance barrier.

## MCP 2026-07-28 and explicit Session capabilities

Only protocol `2026-07-28` is advertised and accepted.

The protocol is stateless and sessionless at the transport layer:

- use `server/discover`;
- do not implement a successful legacy `initialize` path;
- do not advertise older protocol versions;
- do not send, consume or infer identity from `Mcp-Session-Id` or vendor session headers;
- every request must be understandable without a previous transport handshake;
- keep one `/mcp` POST endpoint. Ordinary RPCs and foreground `exec`/custom commands without `_meta.progressToken` return one `application/json` response. With `_meta.progressToken` plus SSE acceptance, foreground `exec` and custom commands return request-scoped `text/event-stream`; `exec_attach` may return request-scoped SSE with or without a progress token because its no-progress mode can long-poll. Never add the deprecated persistent HTTP+SSE `/sse`/GET transport;
- request-scoped process progress uses only standard `notifications/progress` for requests that supplied `_meta.progressToken`. Batch normalized combined process output at a hard 16 KiB maximum or 100 ms, whichever happens first; send no empty progress events, flush any remainder before the final JSON-RPC result, then close the SSE response. The final `exec` result always contains the complete transcript; progress is an additional delivery path, not the only copy;
- HTTP/TLS uses Bun.serve with idleTimeout:0 for long MCP requests. Use the Node standard-library gzip/Brotli streams for negotiated compression and leave text/event-stream uncompressed. Bun owns framing. Stream EOF/error/client cancellation must settle the completion Promise and propagate cancellation upstream; never clone/drain an SSE body before returning it.

Application state uses an explicit Session bearer capability:

- `init_chat_session` accepts no arguments and is the only tool that creates a Session. It always creates a new persistent opaque capability with root id `0` (no selected Workspace), returns `chat_session`, and associates its Tool Call with that new Session. It neither opens nor creates a Workspace. Agents call it once at chat start unless they already hold a valid capability;
- `list_workspaces` is read-only discovery requiring `chat_session`, with no selected Workspace needed. It returns enabled Workspace names plus the common `chat_session` envelope;
- `tools_schema` is an authenticated read-only diagnostic tool requiring `chat_session` but no selected Workspace. It accepts 1–50 unique exact published tool names and returns their canonical complete descriptors from the same `serverTools()` source used by `tools/list`, plus unresolved names in `missing`. Its published `names[]` schema must declare `uniqueItems: true`, and execution must also reject duplicate names explicitly as a runtime defense. Do not remove valid schema constraints to work around a stale ChatGPT conversation: after changing published tool names or schemas, test the refreshed contract from a new chat/branch because an existing conversation may retain its earlier tool-schema snapshot. Never maintain a second descriptor/schema copy for this tool. Returned publication View resource URIs are canonical; the normal `tools/list` cache-busting `?instance=...` suffix is intentionally dynamic and not schema semantics;
- Workspace creation for agents is folded into `open_workspace(create=true)`; there is no public `create_workspace` tool. The internal Desktop-creation helper remains name-only/path-opaque: resolve the current user's Desktop internally without environment-variable home discovery, derive the final directory solely from the name, reject registered-name/registered-effective-path/existing-filesystem-target collisions before touching the filesystem, create the directory non-recursively, then register one enabled Workspace. If directory creation fails, do not touch the database; if later database insertion fails, leave the created directory in place. Linux honors `~/.config/user-dirs.dirs` `XDG_DESKTOP_DIR`; macOS and the core-only Windows fallback use OS-reported home plus `Desktop`;
- `open_workspace` requires an active `chat_session`, a free-string Workspace `name` and optional `create=false`. Validate the capability before any Workspace/filesystem mutation. A missing/disabled Workspace is an error unless `create=true`; a genuinely missing name is explicitly created through the Desktop helper. Attach/move the existing Session and return its unchanged handle. Do not accept `current_context_handle`, `context_handle` or a separate current-session argument, and never create Sessions through Workspace tools;
- `open_workspace` directly returns `workspace_name`, absolute `cwd`, nullable Workspace-level `agent_guidance_path`, `workspace_created`, and a compact `memory_summary` containing live counts plus up to five latest keys for Global, Workspace and Session scope; read guidance when non-null and treat the memory summary only as orientation, not as memory values;
- every base and custom tool except `init_chat_session` requires the same public `chat_session` property, including discovery and diagnostics;
- every tool output schema requires `chat_session` as common metadata, including initialization, `list_workspaces` and `tools_schema`; retain explicit tool-specific output fields;
- every built-in tool must add an explicit tool-specific output schema and use `additionalProperties: false`; never regress to one permissive generic result schema;
- failed calls set `isError: true` and expose one human-readable `error` string; do not add duplicate status, execution, retry, recovery-tool or log-id fields;
- missing, invalid or expired `chat_session` values never execute the requested operation or mint replacements; report an error directing agents to `init_chat_session` only when a new Session is needed;
- valid handles execute and are repeated byte-for-byte in the result;
- Sessions expire after 30 days without activity.

Authentication gates access to the server. After authentication, only `init_chat_session` may execute without a pre-existing Session. Every other tool requires a valid `chat_session`; it selects the Session independently of Workspace selection. Filesystem tools, Workspace preference writes, new processes/custom commands, JavaScript kernels and `publish(path)` require a selected Workspace. Desktop/CDP, discovery, diagnostics, memory, Telegram, OpenRouter and text/Base64 publication may run with no Workspace. Process follow-ups still use the original process Workspace/cwd snapshot and remain available when the Session has no Workspace. Do not bind Sessions, processes or kernels to OAuth clients, Basic credentials or transport identity.

Never describe `chat_session` as a protocol or transport session identifier. Session client metadata is best-effort observational information captured when `init_chat_session` creates the Session; do not infer a model, reasoning/thinking level or client ownership from it. A ChatGPT model or thinking-level change may result in a new Session even inside the same chat.

## Authentication and authorization

Authentication is the only server-access decision.

- Authenticated clients receive all published tools.
- Anonymous clients receive none.
- Do not implement tool approvals, allow/deny regular expressions, enable lists, execution switches or per-tool policy rules.
- OAuth consent remains only to authorize the OAuth client.
- The public OAuth consent/error page remains client-agnostic and server-rendered from its JSX component through renderWebHtml. Escape every dynamic text/attribute with htmlEscape at that web boundary; only MrMCP-owned static style text bypasses escaping. The native GUI never invokes this serializer. Do not rebuild consent with interpolated HTML strings or client-specific copy. Keep it as a compact centered one-screen card using the administration GUI dark palette, with compact client/scope/resource/return rows, green **Authorize Access**, red **Cancel**, matching branded invalid/expired state, and the direct standards-compliant redirect to the registered client callback after the decision. On desktop keep the panel around half the viewport width and size typography from a combination of `vw` and `vh`; do not derive primary consent typography from `vmin`, because a short landscape viewport makes it unacceptably small. Keep logo, spacing and actions viewport-relative, constrain the document to the viewport, and keep all details and both actions visible without scrolling in a normal desktop viewport. Do not add a separate trust-notice block or redundant footer.
- `chat_session` is a bearer capability shared by any authenticated client that possesses it.

## Workspaces and current working directory

The GUI maintains named Workspaces. Workspace names are globally unique; a Workspace may be assigned to many Sessions, while each Session stores exactly one current internal `root_id`.

- Internal Workspace id `0` means no selected Workspace.- `open_workspace(chat_session, name, create?)` is the only agent Workspace opener/creator. Its published `name` remains a free string. With create=false it must resolve to an enabled Workspace; create=true may create a genuinely missing name as one empty Desktop directory through the name-only helper. Existing Workspaces are never replaced. It requires an active Session, selects the Workspace only after validation/guidance lookup succeeds, preserves the same capability, and updates the Tool Call Workspace snapshot to the selected Workspace.
- Workspace reassignment is available both through `open_workspace` and the Workspaces GUI. Sessions shows the current Workspace name/path read-only. Stored relative paths are resolved against `APP_DIR` only when an operation needs an absolute path.
- `open_workspace` checks only the selected Workspace root for guidance, in this priority order: `AGENTS.md`, `agents.md`, `CLAUDE.md`, `Claude.md`, `claude.md`. It returns the first matching absolute guidance path and never scans parent or child directories. It also returns `workspace_created` and a compact `memory_summary` with count/latest-key orientation for both selected Workspace and resulting Session; do not eagerly return memory values there.
- Tool/server descriptions must direct the agent to use the Workspace identity/guidance/Memory-summary fields returned directly by `open_workspace`, explicitly opt into creation only when desired, and read/follow `agent_guidance_path` when non-null. Published tool/input/output schema descriptions should be product-neutral; reserve the `MrMCP` name for actual server identity, branding, UI/resource identity, or behavior where the product name is semantically necessary.

## Processes and PATH

The system-PATH setting is enabled by default.

- `exec` and `exec_start` must describe `args` as the exact ordered argv passed verbatim to the executable; agents should consult the command's `--help` rather than reinterpret uncertain option syntax.
- `exec` is foreground/request-scoped and retains the complete normalized combined stdout/stderr transcript until the call ends. `timeout_ms` defaults to **45,000 ms** and may be raised to **3,600,000 ms**; foreground custom commands use the same contract. High request lifetimes can cross upstream/client retry or replay windows, so descriptors must warn agents and recommend `exec_start` for long/non-idempotent work. Optional client-chosen `operation_id` provides transient replay protection: scope it by exact `(chat_session, tool, operation_id)`, require a canonical match of Workspace plus process arguments excluding `chat_session`/`operation_id`, reuse one process while active and for **5 minutes after completion**, reject mismatched arguments during that window, and permit ordinary reuse after expiry. The key is in-memory only and must never become a permanent Session-wide uniqueness constraint. Without `_meta.progressToken`, `exec` returns one final JSON result after process exit/timeout. With `_meta.progressToken` and SSE support it also emits incremental progress in 16 KiB/100 ms batches, then returns the same complete transcript in the final result. When the HTTP runtime exposes cancellation/disconnect, terminate that child; the selected timeout remains the fallback when disconnect is not surfaced.
- Persistent execution uses `exec_start`, `exec_attach`, `exec_write`, `exec_kill`, `exec_list` and `exec_status`. `exec_start` accepts no client-chosen process label, but may accept the same optional `operation_id` replay key described above. Its returned `exec_id` is exactly the numeric Tool Call log id allocated for the original `exec_start`; matching retries must return that same `exec_id` rather than create another process. `exec_id` remains monotonic/unique and every follow-up lookup is scoped by exact `(chat_session, exec_id)`. Keep the internal random `process_id` and OS PID only for database/GUI/diagnostics. `exec_start` starts immediately, retains the complete normalized stdout/stderr transcript, keeps stdin open, records client stdin writes internally and returns JSON without streaming.
- Retain runtime process output as one ordered normalized chunk ledger carrying stream identity and combined/per-stream character offsets. Never keep parallel resident combined/stdout/stderr transcript strings or a second raw-output copy; materialize combined/separate snapshots or tails only for the response, GUI view or persisted tail that requests them. Preserve observed combined ordering, UTF-16 slice/cursor semantics and exact UTF-8 byte accounting for `exec_attach.remaining_bytes`.
- `exec_attach(exec_id)` consumes unread combined output through an internal cursor and exposes no public offset. Its public `timeout_ms` defaults to **45,000 ms**, may be raised to **3,600,000 ms**, and bounds only that request/attachment; it never terminates the persistent child. With `_meta.progressToken`, emit unread backlog and live output until child exit/kill, disconnect or the bounded attachment timeout, then return the transcript covered by that attachment. Without `_meta.progressToken`, return existing unread data immediately up to 16 KiB; otherwise long-poll only within the same bounded timeout, then return once 16 KiB are available or 100 ms have elapsed after the first new data. `remaining_bytes` is the exact UTF-8 byte count already buffered after the returned chunk. `wait_timed_out=true` means the attachment timeout expired while the process remained running and is distinct from process `timed_out`; agents may immediately attach again or use `exec_status`. Killing/failing while attached must wake the call and preserve final available output/status. Only one attachment may be active per exec id. An observed disconnect or bounded timeout clears that attachment slot and never terminates the persistent child. Do not assume every ordinary JSON socket close is observable before a response exists; the bounded timeout is the mandatory fallback that prevents a stale attachment from surviving into upstream retry windows.
- `exec_write(exec_id)` writes/closes stdin and `exec_kill(exec_id)` terminates only persistent children in the same Session. `exec_list` exposes only currently running persistent executions for the exact `chat_session`; never include completed records there. `exec_status(exec_id)` is read-only/non-consuming and must work for running and retained completed/failed/timed-out/killed records, with `output=none|all|tail`, bounded `tail_lines`, and optional matching stdout/stderr selection through `separate_streams`. Completed in-memory records are retained by the existing 24-hour cleanup window and do not survive server restart. No MCP process input/result may expose internal `process_id` or OS PID.
- ON: prepend `.mrmcp/bin` to the supplied or inherited `PATH`.
- OFF: use only `.mrmcp/bin` in the child `PATH`.
- Managed process environment precedence is system environment → persistent Process Environment `NAME=value` settings → per-call `env`. Parse configured entries by the first `=`, permit empty values, reject malformed/non-portable variable names, preserve later overrides (case-insensitively on Windows), and expand `${MRMCP_DIR}`, `${MRMCP_BIN}`, `${WORKSPACE}` and `${CWD}` only when each process starts. Workspace/CWD placeholders must therefore follow the Session's current Workspace and requested exec cwd dynamically. PATH keeps its separate `inherit_system_path` policy after environment merging.
- The persistent `git_preserve_line_endings` Process Environment setting defaults ON. When enabled, every managed child process must append Git runtime configuration through `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>` so `core.autocrlf=false` overrides machine/user config without modifying it. Preserve existing valid runtime Git config pairs and append MrMCP's pair last, honoring case-insensitive environment names on Windows without duplicate differently-cased count/key/value names; repository `.gitattributes` remains authoritative, and an explicit `git -c core.autocrlf=...` may override the environment default. When the setting is OFF, do not inject the pair. Apply this at the common managed-child environment layer so nested Git invocations inherit it too.
- Use `ComSpec` on Windows and `SHELL` or `/bin/sh` on Unix.
- On Windows, spawn managed `exec` / `exec_start` children through `node:child_process.spawn` with `windowsHide: true` and adapt Node stdio streams to the existing Web Stream process pipeline. Do not regress to a spawn path that flashes a console window or steals native GUI focus. Use the same node:child_process adapter on every platform.
- Managed termination must use the runtime child-process `kill()` API directly. Do not spawn `taskkill`, `kill`, `pkill` or another platform helper and do not claim portable recursive process-tree termination: Bun/Node core provides no cross-platform tree-kill API. `SIGTERM` and `SIGKILL` remain distinct requests on Unix; on Windows Node may terminate the direct child without Unix signal semantics. Parent exit must still release a foreground MCP response after the bounded output-drain path even when descendants retain inherited handles.
- Explicit GUI/`exec_kill` termination uses `termination_source: "user"`; foreground request disconnect/cancellation uses `client`; timeout and server-shutdown requests use `timeout` and `server`, while an externally observable termination uses `external`. Keep `requested_signal` distinct from the actually observed `signal`; do not invent an observed signal when Windows reports none.
- Keep managed process access scoped to the exact `chat_session`; retain the Workspace and cwd snapshot captured at process start.
- `tools_log` is read-only and scoped to the exact `chat_session`. It returns only calls that reached MrMCP and excludes its own currently running log row. Keep `limit` bounded to 1–50 with default 10; `tool` and `status` are exact filters including `invalid`, `query` is a case-insensitive literal substring search across the complete stored log row, and `before_id` is the stable backward-pagination cursor. Filters are combinable. Use it to distinguish server-side execution/validation from upstream/client-wrapper rejection; never claim it can reveal a wrapper policy reason that was not sent to MrMCP.

## Filesystem tools

The built-in filesystem surface is deliberately small and uniform:


- discovery/read: `fs_glob`, `fs_grep`, `fs_read`, `fs_navigate`, `fs_stat`;
- content mutation: `fs_write`, `fs_edit`, `fs_text_convert_encoding_eol`;
- structural mutation: `fs_mkdir`, `fs_copy`, `fs_move`, `fs_trash`, `fs_untrash`.

Do not reintroduce separate single-file/batch variants, a generic `replace` tool, permanent delete, filesystem transaction handles or server-side pagination/navigation state. Prefer these tools over shell commands, `uv`, Python or `js` whenever they express the operation directly. `TOOLS.md` is the human-readable contract and rationale for the published tool surface; keep it synchronized with descriptors and implementation behavior.

All filesystem navigation/search pagination is stateless. `fs_glob` orders paths deterministically in depth-first path-component order and resumes with the explicit `after_path` returned as `next_after_path`. Compare sibling names by locale with an exact string tie-breaker. Traversal, hard-limit collection and both filesystem cursors must use this same total order; never sort only an already-bounded page by a different flat-path order. A continuation may skip a completed subtree only when its component order proves that every descendant precedes the cursor. `fs_grep` resumes with explicit `{path,line}` `resume_after` / `next_resume_after`. `fs_navigate` receives the current line and direction for every file on every call. Never retain hidden server cursors for these tools. `fs_grep` consumes the shared traversal as an async iterator and stops at its result limit; use at most one additional path for lookahead when the current file is exhausted, and never pre-enumerate the remaining tree just to return an early page. Traversal failures remain separate from per-file decoding errors. Cursors refer to live data, not snapshots; do not imply isolation from filesystem changes between calls.

`fs_glob`, `fs_grep` and `fs_trash.selection` share one path-selection model: `path`, globstar `include[]`, globstar `exclude[]`, `gitignore` and `hidden`. `gitignore=true` applies applicable parent `.gitignore` rules and nested `.gitignore` files encountered while descending; do not imply support for Git's index, global excludes or `.git/info/exclude`. Do not add a separate recursive-gitignore switch or dependency-specific traversal policy such as `include_dependencies`. Include-based pruning requires proof from the active patterns that no descendant can match; any global/ambiguous pattern must fail open to the ordinary traversal. Cursor-based pruning additionally permits skipping subtrees proven to precede the continuation in component order. Never hard-code dependency/build/cache directory exclusions: users express those through `.gitignore` or explicit `exclude[]`.

Use explicit names that remain understandable in Tool Call logs. Text context counts are `context_lines_before` / `context_lines_after`, never generic `before` / `after`. Pagination fields identify what they resume (`after_path`, `resume_after`). Trash identifiers are `trash_id`, never generic `action_id`.

`fs_grep` must echo the effective `max_file_bytes` and return page-local `skipped_large_files` for candidates whose observed size exceeds that threshold. Do not count filtered paths, unvisited candidates or lookahead entries until actually examined, and never traverse ahead merely to compute skip totals. Preserve the existing `scanned_files` meaning (examined candidates after path resolution, including oversized files and later decoding failures) and document it explicitly. Per-file errors stay visible independently of oversized-file counts. Zero matches with skipped/error files must not be presented as complete search coverage.

Keep filesystem/retrieval text summaries concise and metadata-only: actual returned/succeeded/failed counts plus relevant continuation-field names. `structuredContent` remains canonical; never duplicate source text, match snippets, fingerprints or complete JSON in the summary, add persisted summaries, or infer success by searching nested payloads. Batch mutation summaries must expose partial/all-entry failures without changing existing call-level completion semantics. Descriptors should distinguish path discovery, textual search, known-file navigation and batched range reads; suggest small optional context when it avoids another read without increasing the default. Prefer suitable discovered catalog commands for symbol/caller/impact exploration; the existing Cymbal entry covers that role, and no LSP integration is needed. Verify skip counters, errors, pagination and summaries together through real tool dispatch, and compare complete verified client workflows when assessing call/output cost.

Support explicit UTF-8, UTF-16LE, UTF-16BE, Windows-1252 and Latin-1 directly in the ordinary text tools, including BOM and `LF`/`CRLF`/`CR` controls. Keep logical text separate from physical representation. The architectural goal is to minimize representation burden on the agent: infer/preserve every byte-level choice that is unambiguous from the source, normalize harmless differences in agent payloads, and require an explicit agent choice only for genuine ambiguity. Do not trade this convenience for permissiveness: malformed input, unsupported text and non-lossless conversions must fail rather than be guessed, substituted or silently repaired. `auto` decoding uses only the charset reported by pinned `chardet`. Settings → Files persists `text_encoding_detection=sample|full`, default `sample`, for `fs_read`, `fs_grep` and `fs_navigate`. Sample mode passes a zero-copy initial 16 KiB byte view (the whole buffer for smaller files) to `chardet`, then strictly decodes the entire original buffer. Use the first candidate returned by the public `chardet.analyse` API only when its confidence score is at least 80. If the candidate is absent, below that confidence threshold, has no charset, or full-buffer decoding fails, retry `chardet.detect` and strict decoding once over the complete original buffer. A sample can miss later charset clues even when decoding succeeds, so keep Complete file available. `fs_write`, `fs_edit` and `fs_text_convert_encoding_eol` always use complete detection whenever source decoding is needed, independent of the read/search setting; low-level decode/read helpers must default to complete detection so mutation callers cannot accidentally opt into sampling. Never use BOM, UTF-8-validity, UTF-16 structure or another local charset heuristic to choose/override a detected charset; fail if the final detection/strict decode fails. Explicit input encodings must bypass `chardet` rather than running detection and discarding its answer. Physical BOM detection remains MrMCP-owned and independent strictly to report factual recognized prefix bytes; never use it for charset selection and never infer it from the selected encoding. Decoder handling of a matching BOM is charset decoding semantics, not detection: custom Unicode decoders must match native `TextDecoder` behavior and consume an initial U+FEFF BOM. Native `TextDecoder` paths stay fatal on malformed input; never fall back to a permissive decoder merely because fatal decoding rejected invalid bytes. Charset-only `iconv-lite` fallback must prove lossless decode/re-encode byte identity before accepting input. Writes must likewise prove that final bytes decode through MrMCP's own path to exactly the requested text, and that requested physical BOM presence/absence matches the bytes, so unsupported characters or malformed Unicode never silently become `?`/replacement characters. Preserve a detected ASCII result as strict ASCII rather than converting it to UTF-8 or relying on the WHATWG `ascii` alias. Do not persist an out-of-band "intended encoding" for ambiguous byte streams: a new UTF-8 file containing only ASCII-compatible bytes may later auto-detect as ASCII, and the pinned detector remains authoritative. Treat BOM as a physical prefix invariant even for explicitly selected legacy encodings: `add` requires a BOM-capable Unicode encoding, but `preserve` on legacy text may succeed naturally when the encoded text itself reproduces the original recognized prefix; never prepend an extra Unicode BOM to legacy payloads. `output_encoding:"preserve"` reuses the detected source charset and defaults to UTF-8 only for a new file; `bom:"preserve"` preserves physical BOM presence and defaults absent only for a new file. `fs_write` must not decode an existing source gratuitously: require decoded source metadata only when preserving its charset, or when preserving line endings and the replacement actually contains breaks; raw BOM presence can be inspected without decoding. Fully explicit whole-file replacement must therefore remain possible even when old bytes are not decodable as text. Reads/searches normalize returned text to LF, never invent a trailing empty line solely because the file ends in a newline, and report empty files as zero text lines. Clamp `fs_read.end_line` to the actual line count before budgeting or iteration; never emit invented rows past EOF. Byte-bounded `fs_read` must prioritize the requested range over optional context: fill the budget with requested lines first, use only remaining space for `context_lines_before` / `context_lines_after`, and paginate only when the requested range itself is incomplete. Context must never displace requested content or cause `next_start_line` to repeat indefinitely; every continuation must advance beyond the requested start. Report `line_endings:"none"` for any text with no CR/LF separator, including both empty and non-empty single-line files. Incoming LF/CRLF/CR or mixed breaks from agent text are logical content only: do not reject them just for differing from the target style, because explicit `line_endings` must normalize all breaks and `preserve` must normalize them to an existing uniform source style. For a new file, `line_endings:"preserve"` defaults to LF and must normalize any incoming LF/CRLF/CR/mixed separators to LF. If an existing source is mixed, return `mixed_line_endings` when a preserved result has breaks; if an existing source has `line_endings:"none"` and the result introduces breaks, return `line_endings_required` and require explicit `lf`, `crlf`, or `cr`. If the resulting text has no breaks, allow `preserve` even for mixed/new/none because the output style is unambiguously `none`. Tool string arguments are already JSON-decoded text: never apply a second C/JavaScript-style escape-decoding pass.

Every tool that reads regular-file content for `fs_read`, a matched `fs_grep` file or `fs_navigate` returns an opaque whole-file `fingerprint`; `fs_stat` may compute one when explicitly requested. Mutation tools accept `expected_fingerprint` per file and return a structured `fingerprint_mismatch` result instead of writing when the current bytes differ. Treat the fingerprint as an opaque concurrency token, not as a public SHA-256 contract even if SHA-256 is the current implementation.

Batch filesystem entries are independent. Do not expose `atomic`, do not roll back successful earlier batch entries because a later entry fails, and do not pretend filesystem operations form an OS transaction. Return structured per-entry status plus `succeeded`/`failed` counts so the agent can see exactly what happened. A single recursive copy/move/trash/untrash may report `failed_partial` when the destination/payload exists after failure; leave that state visible rather than attempting a second best-effort rollback operation. Recursive copy and the cross-filesystem move fallback must preserve symlinks as links rather than dereferencing them.

`fs_edit` is the important local exception: each file is internally all-or-nothing at the edit-validation level. Read the file once, verify `expected_fingerprint` against that initial version, normalize the in-memory edit representation consistently, apply its `edits[]` sequentially to the evolving document so edit N sees edits 1..N-1, validate every `expected_occurrences`, and only then write that file once. If any edit validation fails, do not write that file; continue independently with other files. Duplicate file entries are invalid. Successful results report compact ordered `{index, expected_occurrences, occurrences}` metadata without echoing potentially large `old_text`/`new_text` values.

Filesystem removal is trash-only. There is exactly one MrMCP metadata directory, `APP_DIR/.mrmcp`; named Workspaces never receive a `.mrmcp` directory from MrMCP. `fs_trash` accepts explicit paths and/or one structured selection, collapses nested selected targets, and stores physical payloads from every Workspace under the single `APP_DIR/.mrmcp/trash/<trash_id>/` directory. `trash_id` values are globally unique across both Turso metadata and payload directories and use local date/time to the second with a numeric suffix only on collision. Before moving payloads, insert the transaction and item metadata in Turso so original absolute paths, deterministic payload names, cached type and cached non-directory byte size remain diagnosable; directory size stays unknown even if a later move/crash leaves a missing or partial payload. Do not write sibling JSON manifests. Normal move failures with no retained destination remove their item metadata; retained partial destinations keep it. `fs_untrash` is Workspace-scoped, restores available payloads independently, deletes metadata only after a successful restore, and leaves missing/failed item rows visible for retry/cleanup. Remove a transaction only when no tracked item rows remain. Exclude only the real `APP_DIR/.mrmcp` metadata directory from trash targets/selections; a same-named directory inside an unrelated Workspace is not MrMCP metadata. `fs_trash` and `fs_untrash` are intentionally non-destructive in MCP annotations. Tool Call logs are diagnostics only.
