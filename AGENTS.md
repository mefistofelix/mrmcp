# MrMCP implementation guide

## Current release and files

MrMCP 0.10.154 consists of ten root project files, one GitHub Actions workflow and one versioned asset directory:

- `mrmcp.js` — Deno backend, MCP `2026-07-28`, OAuth/Basic authentication, SQLite, local Tauriless UI and desktop launcher.
- `commands.yaml` — versioned editable extra-command catalog; keep it in the repository root, never under `assets/`.
- `guided_prompts.yaml` — versioned editable MCP guided-prompt catalog; keep it in the repository root, never under `assets/`.
- `proxies.yaml` — authoritative proxy pool/source/cooldown configuration; Settings → Proxies edits it, while proxy outcome statistics live in SQLite. Embed it as a first-run template and preserve user edits.
- `search.yaml` — authoritative Search/OCR and embedding configuration, edited by Settings → Search; embed as a first-run template beside the other YAML catalogs and never overwrite user edits.
- `README.md` — concise current user/operator behavior only; keep release history out of it.
- `CHANGELOG.md` — release history only.
- `AGENTS.md` — implementation invariants and release checks.
- `TOOLS.md` — current built-in tool contracts, arguments, semantics and design rationale.
- `LICENSE` — sole project license file: MIT for MrMCP plus the complete JSONEditor Apache-2.0 notice/text. Embed it in every standalone build; preserve dependency-owned licenses in their packages.
- `.github/workflows/release.yml` — tag-driven GitHub release automation. It must verify `VERSION == tag`, use Deno 2.9.5, build Windows x64 and Linux x64 standalone executables plus native macOS x64/arm64 `MrMCP.app` bundles on matching macOS runners, then create compressed `.dmg` disk images and create/update the GitHub Release with exactly four project-built assets: the two portable binaries and the two DMGs. Do not add checksum/tar/zip archives.
- `assets/` — all static WebView/build assets, including `morphlex.js`, vendored `jsoneditor/` (minimalist JS/CSS/icon; license retained in root `LICENSE`), `mrmcp-logo.svg`, `mrmcp-logo.png`, `mrmcp.ico` and the numbered administration screenshots; do not duplicate them in the repository root.

The only public MCP protocol endpoint is `/mcp`. The public HTTPS listener also serves the read-only unauthenticated `/mrmcp-icon.png` branding asset referenced by MCP `serverInfo.icons`. The administration UI is local-only through Tauriless' `tauri` asset protocol and opens no GUI network listener.

## Desktop shell

The server-authoritative GUI architecture, DOM/Morphlex contract, state ownership, channel semantics and backend/frontend responsibility split are defined directly in this implementation guide. Keep those rules backend-authoritative and portable across the desktop shell; do not reintroduce a second GUI-preference/specification document that can drift from this file.

MrMCP must not import or call Sharp directly. CDP screenshot post-processing uses the public `auto.vips.decodeImage` / `auto.vips.encodeImage` API exported by the installed Auto.js package; never import Auto.js `vips.js` by path. `format=original` performs no image-codec load, while `format=webp` uses that public layer and its current fixed WebP Q=80 plus optional scale. Auto.js is deliberately one normal unversioned latest static `import * as auto from "npm:@mefistofelix/auto.js"`. `desktop_auto` is the only MCP desktop-automation surface: it accepts one AAF YAML scenario and passes it to `auto.run()`; do not expose Auto.js primitives as separate MCP tools or invent a second automation DSL. Preserve arbitrary `results`/final `state`; when final state contains retained WebP/PNG images, recursively keep each image at its original nested state location, remove only binary `data`, insert an `image_id`, deduplicate shared image objects, and emit each distinct image as an MCP `ImageContent` block after the structured JSON text block. These transient model-observation images must never use `publish`, Published storage, MCP Apps or `resource_link`; WebP/PNG plus Auto.js `scale` controls MCP's Base64 wire cost, while AAF `rect` remains absolute screen-space coordinates. Load Tauriless only through the unversioned latest npm literal dynamic import `await import("npm:@mefistofelix/tauriless")` inside `desktop()`, after the backend Worker has started. Never restore a top-level Tauriless import: Tauriless eagerly calls `Deno.dlopen` during module evaluation, so the same `mrmcp.js` being evaluated by the main isolate and backend Worker would load the native bridge twice in one process; on macOS that can register duplicate Objective-C classes and break WebView bootstrap. Resolve Tauriless from npm latest at check/build time and configure desktop identity before the first WebView through the single cross-platform `tauriless:set-app-user-model-id` bridge.

- Do not add a hand-written FFI wrapper, vendored Tauriless native binaries, a Rust/Tauri scaffold, Neutralinojs, a Node.js application, npm project files or a separate CLI scaffold. The only command-line modes are the normal desktop launch, `--backend`, and one-shot `--add-workspace <name> <path>` handled directly by `mrmcp.js`. Tauriless is consumed only as the normal npm JS library and owns its native binding internally.
- Desktop mode is one OS process: Tauriless stays on the main OS thread and Deno repeatedly calls `tauriless.run(16)`, giving the native event loop a bounded 16 ms slice before Deno resumes its own event loop; the backend runs in a named Deno Worker/isolate loaded from the same `mrmcp.js`. Readiness and shutdown use typed Worker messages (`ready`, `shutdown`, `stopped`), not stdout parsing or a child process. Tauriless serves the GUI through `asset-request` / `tauriless:asset-response` with inline `content`; the GUI has no loopback HTTP listener, login token, cookie, session or CSRF layer. Browser inputs use Tauri `plugin:event|emit`; Deno renders in the Worker, posts the render to the main thread, and the main thread delivers it with `plugin:event|emit_to`. The WebView must register `tauri://close-requested` immediately with the static `main` Window target so Tauri does not destroy the window, but this listener is independent from the MrMCP render-event/bootstrap chain: never gate GUI bootstrap on it and never read `__TAURI_INTERNALS__.metadata.currentWindow` during startup. The Tauriless main-thread drain remains responsible for reacting to the forwarded close request by hiding `main`. The main thread also owns native window visibility detection and sends typed `ui-visibility` messages to the Worker. Hidden or minimized windows must not cause backend UI projection, Eta rendering, HTML construction or Worker→WebView render delivery; Deno state/data still updates and the render queue remains dirty until one fresh full-state render is requested when the window becomes visible and non-minimized again. Closing the Tauriless window requests graceful backend shutdown and then terminates the Worker only as a bounded fallback. Worker wait timeouts must clear their timers when readiness/shutdown wins; after desktop cleanup completes, the main entrypoint exits explicitly so FFI or other residual handles cannot keep `mrmcp.exe` resident.
- The initial desktop size is 1180×760.
- Release builds target Windows x64, Linux x64, macOS x64 and macOS arm64. Each compile must exclude Tauriless native directories and Tree-sitter .node bindings belonging to other targets; retain the Intel macOS companion binding only for macOS x64, and retain the npm package Xberg WASM only for macOS x64. Resolve dependency directories from deno info --json npmPackages.localPath at build time, never hard-code a user cache path, modify vendor packages or omit the required target binding. Preserve package metadata and JS loaders. Document search uses LanceDB 0.22.3 on Intel macOS and 0.27.2 elsewhere; cache the public native package metadata for every release target before generating excludes, then exclude native LanceDB binaries of other targets and unused versions while retaining JS/metadata. Cross compilation resolves optional packages after deno info, so inspecting only host packages is insufficient. Windows/Linux are produced on Linux; macOS builds run natively on `macos-15-intel` / `macos-15`, package the standalone executable as `MrMCP.app`, then place that bundle plus an `Applications` link inside a compressed read-only `.dmg`. The Tauriless npm latest package must bundle `win32-x64`, `linux-x64`, `darwin-x64` and `darwin-arm64` native bridges. Because Deno 2.9 applies a default 24-hour minimum dependency age, release CI must pass `--minimum-dependency-age=0` to check/compile so the current npm latest dependencies can be consumed immediately. Windows standalone builds must use both `deno compile --no-terminal` and `--icon assets/mrmcp.ico` so the compiled desktop application opens only the WebView, has the MrMCP executable icon and does not create a companion console window. Never omit either flag from release builds. After any local source change that can affect the standalone application, always regenerate the local `mrmcp.exe` before finishing so the current build is immediately testable; do not leave source and executable out of sync. Invalid/failure bodies append one compact `⚠️` error line after tool/command details. When the original MCP request supplied `_meta.progressToken`, every Tool Call start/outcome notification also appends `📡 Progress requested`; do not place that transport flag inside the tool argument preview. Use bullets/newlines when a notification contains multiple facts or Workspace names. The Tauriless main thread performs every native notification call. ## Database: direct current schema with a recreate-only version gate

The repository is in development. There is no backward-compatibility or migration layer. `schema_meta(id=1,version)` plus `DB_SCHEMA_VERSION` is only a fail-fast recreate boundary for the exact current schema.

1. Use only `schema_meta(id=1,version)` / `DB_SCHEMA_VERSION` for schema compatibility detection. Do not add `PRAGMA user_version`, migration tables or a second version mechanism.
2. Prefer extending an existing logical table over creating auxiliary tables whose only purpose is compatibility or carrying fields that naturally belong on that table. Do not create a separate compatibility table when adding fields to the existing current-schema table is simpler. Ensure genuinely distinct current tables/indexes directly at startup with `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`.
3. Do not add schema migrations, compatibility backfills or startup `ALTER TABLE` mutations. A clean database creates the exact current schema and records the current version. Inspect existing `.mrmcp/mrmcp.sqlite` before normal startup, temporary-file cleanup or sidecar materialization. An unversioned or differently-versioned database opens a local desktop recovery confirmation showing the current data directory and proposed sibling `.mrmcp.backup-YYYYMMDD-HHmmss` path. Only Start Fresh renames the entire old `.mrmcp` directory, including SQLite WAL and all other state, then starts with a new current-schema directory; never overwrite an existing backup, import old data or delete the old database. Quit leaves the old data in place. Reuse the same Tauriless instance/window when continuing into the normal GUI. Headless/one-shot modes ask through an interactive terminal only; unattended input must fail with recovery instructions without resetting anything or loading GUI assets. Settings must display the absolute active data-directory path in every tab.
4. The schema-version check is fail-fast validation, never a migration framework. Keep the clean current schema authoritative and remove obsolete tables/columns rather than retaining compatibility shapes.
5. Never import legacy configuration keys or identifiers.
6. Never retain an old table or column only for compatibility.
7. Never accept legacy `opaque_` values, `server_opaque` arguments or transport-derived session identifiers.
8. A clean schema must create no named `default` Workspace and `roots.name` must be globally unique with `UNIQUE(name)`, never `UNIQUE(server_id,name)`.
9. `contexts.id` is the numeric administrative Session primary key; `contexts.handle` remains the unique opaque Session bearer capability. Tool Call and process-history rows retain both `context_id` and internal `context_handle` snapshots. `logs.progress_requested` is transport metadata stored directly on the Tool Call row and never injected into tool arguments. Every Tool Call receives one stable integer id before execution; `exec_start` returns that same Tool Call id as public `exec_id` regardless of whether history storage is Disk or Memory. Disk rows live in the main database; Memory rows live only in SQLite TEMP structures and disappear on restart. `process_runs` is always a main-database process-subsystem table independent of Tool Call Disk/Memory storage; `process_runs.log_id` is only a correlation to the originating Tool Call id and may outlive that Tool Call history row. HTTP diagnostic rows keep their historical Session/Workspace association in additive `debug_log_workspaces(debug_log_id PRIMARY KEY, context_id, root_id, root_name, root_path)` with `ON DELETE CASCADE`; the HTTP Log must never derive a historical Workspace label from the Session's later current `root_id`. Context rows may retain observational creation-client metadata (auth kind, OAuth client id/name and User-Agent); that metadata never owns or authorizes the Session. Tool Call ids must never be reset or reused.
10. Settings **Clear Operational Data** is a history/data cleanup, not a configuration reset: preserve `proxy_stats`, `config`, `server_config`, `custom_tools`, all OAuth tables, `roots`, `contexts`, `memories`, `cdp_browsers`, `cdp_targets`, `trash_transactions`, `trash_items` and the persistent `.mrmcp/cdp/` browser profiles; clear both Disk and Memory Tool Call history plus FTS/descriptors, completed/orphaned process-history records while preserving active process rows/runtime, HTTP log rows plus Workspace snapshots, every row in shared `published` plus its `.mrmcp/publish/` payload snapshots, and reset metrics. After the main-database deletion transaction commits, run `VACUUM` followed by `PRAGMA wal_checkpoint(TRUNCATE)` so freed SQLite pages and WAL storage are returned to disk. Reset the `debug_logs` sequence only; never reset Tool Call ids. Page-level confirmed Clear actions remain required: Tool Calls clears both history tiers without stopping already-detached persistent processes; Sessions deletes every Session after draining in-flight Tool Calls and requests termination of running persistent processes owned by those Sessions while preserving Tool Call history snapshots; Workspaces deletes every named Workspace and moves Sessions to root id `0` without touching files or running processes; OAuth Clients removes all OAuth clients/codes/access/refresh tokens while preserving Sessions and Basic authentication; HTTP Log clears HTTP rows plus `debug_log_workspaces`. Dashboard **Empty Trash** permanently removes the contents of the single `APP_DIR/.mrmcp/trash` store plus `trash_transactions` / `trash_items` metadata. Tool-Call-dependent maintenance uses one Promise barrier rather than an application queue: new Tool Calls wait, already in-flight Tool Calls finish, maintenance runs, then waiting Tool Calls continue. Maintenance dialogs are confirmation-only and long-running maintenance reports completion/failure through the Deno-owned notice balloon. Dashboard always exposes `activeCallControls.size` as Tool Calls In Flight. Clear Operational Data must not delete certificates, command files/catalog data, trash contents or Workspace files outside dedicated publish snapshots.
11. Tool Call history has two independent operator policies. **Storage** is `disk` or `memory`: Disk survives restart in the main SQLite database; Memory uses SQLite TEMP tables/FTS on the same connection and is volatile. **Payload retention** is `payload` or `metadata`: Payload stores exactly one canonical serialized MCP JSON-RPC request packet and one canonical serialized MCP JSON-RPC response packet; Metadata keeps identity/Session/Workspace/status/timing/progress plus bounded errors but stores neither packet. Do not persist secondary Tool Call copies of arguments, structured returns, stdout/stderr, MCP transport additions or extracted binary payloads. Binary/image/text interpretation for debugging is derived from the canonical packets only when a Tool Call detail is viewed. Historical tool descriptors remain separate deduplicated schema snapshots because they describe the tool contract seen by that call rather than duplicate its transport payload. Payload policy is observability only: it must never remove state required for a feature. Persistent-process command/output state, Browser rings, Memory, Published data, CDP state and other functional subsystems retain whatever they need independently of Tool Call payload mode. GUI/tools must inspect each row's actual capabilities (storage/payload/field presence), not branch on the current global setting except in Settings itself. Disk retention uses `tool_call_retention_hours` (`0` = indefinite); Memory retention uses `tool_call_memory_retention_minutes` (default 60, `0` = until restart). Retention removes only completed eligible Tool Call history in its own tier and never deletes process/CDP or other functional subsystem state. Routine retention must never VACUUM. Keep configuration/server/tool descriptors cached coherently, derive Session statistics with indexed aggregate queries instead of a mutable Session-stats cache, use bounded SQLite busy timeout and prepared-statement cache, batch low-value request metrics, and index canonical packets asynchronously through contentless FTS5 without duplicating source text. Database mutation effects must be explicit at semantic operation boundaries: never regex-parse SQL text to infer cache invalidation or GUI render scopes. `structuredContent` is the canonical structured MCP result; the required text content for structured tools must stay concise rather than pretty-printing another complete JSON copy. Normal Tool Calls remain concurrent except for the maintenance barrier.

## MCP 2026-07-28 and explicit Session capabilities

Only protocol `2026-07-28` is advertised and accepted.

The protocol is stateless and sessionless at the transport layer:

- use `server/discover`;
- do not implement a successful legacy `initialize` path;
- do not advertise older protocol versions;
- do not send, consume or infer identity from `Mcp-Session-Id` or vendor session headers;
- every request must be understandable without a previous transport handshake;
- keep one `/mcp` POST endpoint. Ordinary RPCs and foreground `exec`/custom commands without `_meta.progressToken` return one `application/json` response. With `_meta.progressToken` plus SSE acceptance, foreground `exec` and custom commands return request-scoped `text/event-stream`; `exec_attach` may return request-scoped SSE with or without a progress token because its no-progress mode can long-poll. Never add the deprecated persistent HTTP+SSE `/sse`/GET transport;
- request-scoped process progress uses only standard `notifications/progress` for requests that supplied `_meta.progressToken`. Batch normalized combined process output at a hard 16 KiB maximum or 100 ms, whichever happens first; send no empty progress events, flush any remainder before the final JSON-RPC result, then close the SSE response. The final `exec` result always contains the complete transcript; progress is an additional delivery path, not the only copy;
- HTTP content compression belongs to Deno. Both public `Deno.serve` listeners must use `automaticCompression: true`; do not add a hand-written zlib/Brotli/gzip response middleware, `Content-Length` gate, chunk encoder or compressor-flush layer. Deno owns content-encoding negotiation/compressibility and the HTTP runtime owns framing. Current Deno leaves `text/event-stream` uncompressed even when ordinary compressible text/JSON responses negotiate gzip/Brotli; preserve that native behavior rather than adding an SSE-only compressor.

Application state uses an explicit Session bearer capability:

- `init_chat_session` accepts no arguments and is the only tool that creates a Session. It always creates a new persistent opaque capability with root id `0` (no selected Workspace), returns `chat_session`, and associates its Tool Call with that new Session. It neither opens nor creates a Workspace. Agents call it once at chat start unless they already hold a valid capability;
- `list_workspaces` is read-only discovery requiring `chat_session`, with no selected Workspace needed. It returns enabled Workspace names plus the common `chat_session` envelope;
- `tools_schema` is an authenticated read-only diagnostic tool requiring `chat_session` but no selected Workspace. It accepts 1–50 unique exact published tool names and returns their canonical complete descriptors from the same `serverTools()` source used by `tools/list`, plus unresolved names in `missing`. Its published `names[]` schema must declare `uniqueItems: true`, and execution must also reject duplicate names explicitly as a runtime defense. Do not remove valid schema constraints to work around a stale ChatGPT conversation: after changing published tool names or schemas, test the refreshed contract from a new chat/branch because an existing conversation may retain its earlier tool-schema snapshot. Never maintain a second descriptor/schema copy for this tool. Returned publication View resource URIs are canonical; the normal `tools/list` cache-busting `?instance=...` suffix is intentionally dynamic and not schema semantics;
- Workspace creation for agents is folded into `open_workspace(create=true)`; there is no public `create_workspace` tool. The internal Desktop-creation helper remains name-only/path-opaque: resolve the current user's Desktop internally without environment-variable home discovery, derive the final directory solely from the name, reject registered-name/registered-effective-path/existing-filesystem-target collisions before touching the filesystem, create the directory non-recursively, then register one enabled Workspace. If directory creation fails, do not touch the database; if later database insertion fails, leave the created directory in place. Linux honors `~/.config/user-dirs.dirs` `XDG_DESKTOP_DIR`; macOS and the core-only Windows fallback use OS-reported home plus `Desktop`;
- `open_workspace` requires an active `chat_session`, a free-string Workspace `name` and optional `create=false`. Validate the capability before any Workspace/filesystem mutation. A missing/disabled Workspace is an error unless `create=true`; a genuinely missing name is explicitly created through the Desktop helper. Attach/move the existing Session and return its unchanged handle. Do not accept `current_context_handle`, `context_handle` or a separate current-session argument, and never create Sessions through Workspace tools;
- `open_workspace` directly returns `workspace_name`, absolute `cwd`, nullable Workspace-level `agent_guidance_path`, `workspace_created`, and a compact `memory_summary` containing live counts plus up to five latest keys for Global, Workspace and Session scope; read guidance when non-null and treat the memory summary only as orientation, not as memory values;
- every base and custom tool except `init_chat_session` requires the same public `chat_session` property, including discovery and diagnostics;
- every tool output schema requires `chat_session` as common metadata, including initialization, `list_workspaces` and `tools_schema`; retain explicit tool-specific output fields;
- every built-in tool must add an explicit tool-specific output schema and use `additionalProperties: false`; never regress to one permissive generic result schema;
- failed calls set `isError: true` and expose one human-readable `error` string; do not add duplicate status, execution, retry, recovery-tool or log-id fields;
- missing, invalid or expired `chat_session` values never execute the requested operation or mint replacements; report an error directing agents to `init_chat_session` only when a new Session is needed;
- valid handles execute and are repeated byte-for-byte in the result;
- Sessions expire after 30 days without activity.

Authentication gates access to the server. After authentication, only `init_chat_session` may execute without a pre-existing Session. Every other tool requires a valid `chat_session`; it selects the Session independently of Workspace selection. Filesystem tools, Workspace preference writes, new processes/custom commands, JavaScript kernels and `publish(path)` require a selected Workspace. Desktop/CDP, discovery, diagnostics, memory, Telegram and text/Base64 publication may run with no Workspace. Process follow-ups still use the original process Workspace/cwd snapshot and remain available when the Session has no Workspace. Do not bind Sessions, processes or kernels to OAuth clients, Basic credentials or transport identity.

Never describe `chat_session` as a protocol or transport session identifier. Session client metadata is best-effort observational information captured when `init_chat_session` creates the Session; do not infer a model, reasoning/thinking level or client ownership from it. A ChatGPT model or thinking-level change may result in a new Session even inside the same chat.

## Workspaces and current working directory

The GUI maintains named Workspaces. Workspace names are globally unique; a Workspace may be assigned to many Sessions, while each Session stores exactly one current internal `root_id`.

- Internal Workspace id `0` means no selected Workspace. Only document_grep and source_code_search may use the explicitly configured Search default_path, initially OS Desktop/_default, without assigning a Workspace. It never supplies a filesystem base to ordinary file/process/kernel tools. New chat Sessions begin at id `0`; it is not a named Workspace accepted by `open_workspace`. The GUI displays No Workspace and an empty path; prompts expose `workspace:null` for such Sessions. Keep existing SQLite identity columns, including internal `context_handle` snapshots, unchanged: the public argument/envelope rename does not require a database schema change.
- `open_workspace(chat_session, name, create?)` is the only agent Workspace opener/creator. Its published `name` remains a free string. With create=false it must resolve to an enabled Workspace; create=true may create a genuinely missing name as one empty Desktop directory through the name-only helper. Existing Workspaces are never replaced. It requires an active Session, selects the Workspace only after validation/guidance lookup succeeds, preserves the same capability, and updates the Tool Call Workspace snapshot to the selected Workspace.
- Workspace reassignment is available both through `open_workspace` and the Workspaces GUI. Sessions shows the current Workspace name/path read-only. Stored relative paths are resolved against `APP_DIR` only when an operation needs an absolute path.
- `open_workspace` checks only the selected Workspace root for guidance, in this priority order: `AGENTS.md`, `agents.md`, `CLAUDE.md`, `Claude.md`, `claude.md`. It returns the first matching absolute guidance path and never scans parent or child directories. It also returns `workspace_created` and a compact `memory_summary` with count/latest-key orientation for both selected Workspace and resulting Session; do not eagerly return memory values there.
- Tool/server descriptions must direct the agent to use the Workspace identity/guidance/Memory-summary fields returned directly by `open_workspace`, explicitly opt into creation only when desired, and read/follow `agent_guidance_path` when non-null. Published tool/input/output schema descriptions should be product-neutral; reserve the `MrMCP` name for actual server identity, branding, UI/resource identity, or behavior where the product name is semantically necessary.
- Changing a Session Workspace affects new calls immediately. Existing background and interactive processes continue with their original working directory.
- Disabling or deleting a Workspace moves associated Sessions to internal id `0` without terminating processes; such Sessions remain visible for operator reassignment but new Sessions cannot be opened into id `0` through `open_workspace`.
- Resolve the Session and Workspace once at the start of each call and use that fixed selection for the whole operation.

All ordinary filesystem paths and new child-process working directories must remain inside the selected Workspace. Retrieval paths stay inside either the selected Workspace or the configured Search default directory; returned source_directory/index_directory/workspace_selected make that effective scope explicit.

JavaScript kernels are lazy and keyed internally by `(server_id, chat_session, root_id)`. Switching Workspaces selects or creates the matching kernel; switching back restores its previous state. Never share a kernel between different Sessions.

### UI design rationale and non-negotiable state model

The GUI uses one simple server-owned state machine. This rule exists because a previous unified-event refactor left sidebar clicks unable to change section: events were emitted, but there was no authoritative state transition and no guaranteed render path. Do not solve this class of problem with imperative DOM patches.

Every value that can change what the operator sees is graphical state and belongs to Deno, including apparently small values such as:

- the current sidebar section;
- which Tool-call or HTTP-log row is expanded;
- current filters, page number and page size;
- open/closed dialogs, confirmation targets and validation messages;
- form drafts, selected values, focus/selection metadata and per-section scroll positions;
- temporary outputs such as self-test results and live/reconnecting state.

Use stable identifiers for state that points at persistent data. An expanded row is stored as its database primary key, never as a row index, table position, DOM id derived from position or copied row object. This lets Eta reconstruct the same visible state after unrelated MCP, process or log activity.

The authoritative flow is always:

1. The WebView observes user activity and coalesces only noisy state updates before crossing the Tauri bridge: text `input` changes are debounced for 60 ms and merged by control id, scroll is debounced for 80 ms, and pending focus/scroll/input envelopes may collapse latest-wins in the WebView send queue. Click/action/change/blur/submit/navigation are semantic events: never debounce/drop them; flush pending text input first, then enqueue the semantic event in order.
2. Deno receives the already-coalesced envelopes and validates/processes every received event strictly sequentially. Do not add a second latest-wins/debounce/coalescing layer in Deno.
3. Deno updates `uiState` where required and performs database, filesystem, process, TLS, OAuth or command work.
4. Deno marks the UI dirty instead of rendering synchronously in the mutation path.
5. If the native window is hidden or minimized, stop there: retain only the dirty state while all authoritative Deno/DB/runtime state continues changing normally.
6. If the native window is visible and non-minimized, the render scheduler coalesces/throttles bursts and asynchronously builds the active view with Eta.
7. The backend Worker posts the completed HTML plus restoration metadata to the main thread, which emits it to the WebView over the Tauri event bus.
8. The WebView applies only the newest render revision through unmodified Morphlex with `preserveChanges: true`. Do not patch Morphlex or add form-state snapshots/replay/callback workarounds: use its built-in dirty-control semantics so user edits survive ordinary morphs while fresh server-rendered controls and later authoritative server changes can still establish values normally. Stable DOM ids should be used when stable node identity matters. A surviving enabled active form control keeps its native focus/selection; stale Deno focus metadata must not move its caret. Structural removal/replacement has normal browser effects. A hidden→visible transition forces one current full-state render; never replay intermediate hidden updates.

The same path applies to non-user events. A new MCP tool call, a log row, process output/completion, a Workspace change, OAuth mutation, certificate update or settings change must update backend state/data and enqueue the same render pipeline. There must not be a separate “automatic refresh” implementation.

Eta is responsible for conditional UI composition. It selects the visible section from `uiState.currentSection` with ordinary conditionals and renders only that section. Data access must be lazy and section-scoped: the projection or helper for Tool calls queries Tool-call data only while Tool calls is active; HTTP-debug data is queried only while HTTP debug is active; the same rule applies to every section. Do not preload every page merely because a full `#app` HTML fragment will be sent.

The WebView is deliberately not a second application runtime. It must not decide what section is active, toggle expanded rows locally, retain dialog state, fetch business data, or patch UI state with `classList`, `hidden`, injected rows or hand-built HTML. Apart from transport bookkeeping and applying Morphlex output, visible changes originate from Deno-rendered Eta HTML.

If a new interaction appears to require browser-local state, first add an explicit field to Deno `uiState` and route the interaction through the normalized input dispatcher. Exceptions require a concrete technical reason and must be documented here.

### Deno owns all ephemeral UI state

The WebView must not own an application-state object. Do not add `globalThis.mrmcpUiState`, browser-side section state, browser-side pagination state, browser-side expanded-row state or browser-side dialog state.

Deno owns one ephemeral `uiState` object containing at least:

- `currentSection` and per-section scroll positions;
- focus/selection metadata;
- the optional Sessions OAuth-client filter;
- command filters and pagination;
- guided-prompt filters, pagination and prompt drafts;
- Tool-call tool/command query, generic query, Session-PK/status filters, pagination, self-test output and expanded log primary key;
- HTTP-debug filters and expanded row primary key;
- Workspace, Command and Settings drafts, the active Settings tab, plus inline field-validation state;
- active confirmation/form dialog and non-modal notice balloon.

Database primary keys identify expanded rows. Never use a row index or DOM position.

### Thin WebView transport

The embedded browser has only transport and DOM-application responsibilities:

1. delegate user events;
2. serialize them and emit them through Tauri `plugin:event|emit`;
3. receive render payloads through Tauri `plugin:event|listen` after the main thread sends them with `plugin:event|emit_to`;
4. morph the complete `#app` HTML using Morphlex;
5. apply scroll/focus metadata sent by Deno.

The browser must not call `/api/state`, `/api/render` or section-specific JSON endpoints. It must not execute database, filesystem, process, TLS, OAuth or command business logic. Local clipboard writes are allowed because they carry no persistent or graphical application state. Native drag `DataTransfer` may transiently carry only a numeric Session PK to a server-rendered Workspace drop target; it must not add/remove classes, move nodes, retain assignment state or otherwise alter visible UI locally.

### One backend input and render pipeline

WebView→backend delivery is ordered and source-coalesced in the WebView only. Text `input` events use a 60 ms debounce and merge by control id so the newest value for every changed control survives; scroll uses an 80 ms debounce; pending `inputs`, focus and scroll envelopes may replace an older pending envelope of the same type while still in the WebView send queue. Action/change/blur/submit/navigation and other semantic events are barriers: flush pending text input before them and never drop or reorder them. Deno must not coalesce again: it processes every envelope that crossed the bridge one at a time, in arrival order. The dispatcher updates `uiState`, performs the requested backend action and queues a render when required. Backend-originated changes from MCP calls, logs, managed processes, Workspaces, OAuth, TLS, settings and commands enter the same render pipeline through `emitUiChange`.

Rendering must not occur synchronously in mutation paths:

- use a short throttle to coalesce bursts;
- permit only one render at a time and assign every dirtying request a monotonically increasing render generation;
- if another event arrives during model/Eta construction, mark the current generation stale, abort cooperatively at the next async/yield boundary, discard the partial/intermediate HTML and restart exactly once from the newest generation; never finish or deliver intermediate renders when a newer state is already known;
- model building and every Eta fragment render must check the current generation before and after asynchronous work, so a burst does not repeatedly construct obsolete full HTML;
- yield before expensive work;
- gate the expensive path on native `visible && !minimized`; while false, retain `uiRenderQueued` only and do not call `buildUiRenderModel()`, Eta, HTML construction or Worker/WebView render delivery;
- if visibility becomes false during an already-started render, discard its finished payload and leave the queue dirty;
- when visibility becomes true, force one fresh complete render from the current Deno state regardless of how many hidden changes occurred;
- use Eta asynchronous rendering when available;
- send the completed full `#app` HTML through the Worker → main-thread → Tauri event path only while visible;
- main-thread→WebView render delivery is serialized with one in-flight payload plus one latest pending slot: while a render is in flight, replace the pending slot with the newest revision and skip every intermediate revision; the WebView also rejects any revision not newer than the last applied one.

Do not add interval polling, refresh timers, auto-refresh controls, manual refresh paths, hidden-render replay queues or multiple independent render queues.

## Processes and PATH

The system-PATH setting is enabled by default.

- `exec` and `exec_start` must describe `args` as the exact ordered argv passed verbatim to the executable; agents should consult the command's `--help` rather than reinterpret uncertain option syntax.
- `exec` is foreground/request-scoped and retains the complete normalized combined stdout/stderr transcript until the call ends. `timeout_ms` defaults to **45,000 ms** and may be raised to **3,600,000 ms**; foreground custom commands use the same contract. High request lifetimes can cross upstream/client retry or replay windows, so descriptors must warn agents and recommend `exec_start` for long/non-idempotent work. Optional client-chosen `operation_id` provides transient replay protection: scope it by exact `(chat_session, tool, operation_id)`, require a canonical match of Workspace plus process arguments excluding `chat_session`/`operation_id`, reuse one process while active and for **5 minutes after completion**, reject mismatched arguments during that window, and permit ordinary reuse after expiry. The key is in-memory only and must never become a permanent Session-wide uniqueness constraint. Without `_meta.progressToken`, `exec` returns one final JSON result after process exit/timeout. With `_meta.progressToken` and SSE support it also emits incremental progress in 16 KiB/100 ms batches, then returns the same complete transcript in the final result. When the HTTP runtime exposes cancellation/disconnect, terminate that child; the selected timeout remains the fallback when disconnect is not surfaced.
- Persistent execution uses `exec_start`, `exec_attach`, `exec_write`, `exec_kill`, `exec_list` and `exec_status`. `exec_start` accepts no client-chosen process label, but may accept the same optional `operation_id` replay key described above. Its returned `exec_id` is exactly the numeric Tool Call log id allocated for the original `exec_start`; matching retries must return that same `exec_id` rather than create another process. `exec_id` remains monotonic/unique and every follow-up lookup is scoped by exact `(chat_session, exec_id)`. Keep the internal random `process_id` and OS PID only for database/GUI/diagnostics. `exec_start` starts immediately, retains the complete normalized stdout/stderr transcript, keeps stdin open, records client stdin writes internally and returns JSON without streaming.
- Retain runtime process output as one ordered normalized chunk ledger carrying stream identity and combined/per-stream character offsets. Never keep parallel resident combined/stdout/stderr transcript strings or a second raw-output copy; materialize combined/separate snapshots or tails only for the response, GUI view or persisted tail that requests them. Preserve observed combined ordering, UTF-16 slice/cursor semantics and exact UTF-8 byte accounting for `exec_attach.remaining_bytes`.
- `exec_attach(exec_id)` consumes unread combined output through an internal cursor and exposes no public offset. Its public `timeout_ms` defaults to **45,000 ms**, may be raised to **3,600,000 ms**, and bounds only that request/attachment; it never terminates the persistent child. With `_meta.progressToken`, emit unread backlog and live output until child exit/kill, disconnect or the bounded attachment timeout, then return the transcript covered by that attachment. Without `_meta.progressToken`, return existing unread data immediately up to 16 KiB; otherwise long-poll only within the same bounded timeout, then return once 16 KiB are available or 100 ms have elapsed after the first new data. `remaining_bytes` is the exact UTF-8 byte count already buffered after the returned chunk. `wait_timed_out=true` means the attachment timeout expired while the process remained running and is distinct from process `timed_out`; agents may immediately attach again or use `exec_status`. Killing/failing while attached must wake the call and preserve final available output/status. Only one attachment may be active per exec id. An observed disconnect or bounded timeout clears that attachment slot and never terminates the persistent child. Do not assume every ordinary JSON socket close is observable before a response exists; the bounded timeout is the mandatory fallback that prevents a stale attachment from surviving into upstream retry windows.

## Persistent memory

## Published content and MCP App widget

`publish` is the single supported user-publication surface. Keep the contract stateless across Tool Calls and deliberately source-oriented:

- every call supplies exactly one of `path`, `text` or `base64`, plus required `mime_type`; never add a transient `image_id`/previous-result lookup or another cross-call cache. `path` snapshots an existing regular Workspace file, `text` is encoded as UTF-8 bytes, and `base64` is decoded directly. `filename` is optional; path defaults to its source basename while direct content gets a MIME-based fallback name. `title`, `description` and `height` are presentation metadata. `presentation=auto|inline|download` is only a smart-widget hint and must never override the actual MIME-driven HTTP delivery semantics;
- all three source forms enter the same serialized publication chain and end as ordinary physical files under `.mrmcp/publish/`, named with the random public capability id prefix plus a sanitized presented filename. Do not store HTML/text/Base64 payloads inline in SQLite or maintain a separate HTML persistence path. File-origin publications retain their source path/name metadata; direct text/Base64 publications have no source path. Publications remain immutable snapshots after creation and survive source changes/moves/deletion and backend restarts until explicit Published Delete, Published Clear Matching or Clear Operational Data removes them;
- use one fast deterministic `content_key` algorithm for every source: SHA-256 over size plus first 10 bytes, last 10 bytes and central 10 bytes. Never hash a whole large file merely for deduplication. The random `published.id` remains the persistent public capability and must not be replaced by the content key. Equal non-empty content keys within a server reuse one physical snapshot. `published_uses` remains a relationship table with at most one current relation per published item + Session + call-time Workspace; repeat publication in the same relation updates source/display/MIME/title/description/presentation/height metadata and timestamp, while another Workspace gets a distinct relation without another payload copy;
- the public content capability URL is `/published/<id>/<filename>`. The filename suffix is presentational: a valid id remains sufficient to address the resource and a matching relation may provide its current filename/MIME metadata. Always include the sanitized filename in `Content-Disposition`. Browser-displayable MIME types use `inline`; opaque/binary/executable MIME types use `attachment`. The agent's `presentation` hint affects only the widget, never these response semantics. The returned `structuredContent.uri` is this actual content URL, not the MCP App resource URL;

## Filesystem tools

The built-in filesystem surface is deliberately small and uniform:

`source_code_search` is the separate Lucerna source-retrieval surface. Use only public `TreeSitterChunker` and `Searcher` APIs, with a persistent MrMCP-owned `node:sqlite` FTS5/BM25 store; do not modify vendor code, evaluate Workspace Lucerna configuration, launch a second MCP/Node process, install embeddings or send source to a provider. The current deployment exposes only `search`, `map`, `files`, `chunks` and `stats`, reporting mode `lexical`. Semantic embeddings and call-graph actions are unavailable in this build; never describe lexical ranking or an empty unsupported graph as semantic/caller analysis. Native package imports must remain lazy: parser 1.6.2 is pinned through its package.json import because current optional dependencies are incompletely published, and the Intel macOS companion is an ordinary npm package consumed by the parser's own NAPI_RS_NATIVE_LIBRARY_PATH loader option. Resolve both public npm entries with import.meta.resolve and fileURLToPath so source and compiled VFS paths work, synchronously require the main parser under that temporary option and restore the previous environment value in finally before awaiting Lucerna. Never replace the vendor loader or hand-load a .node/FFI binding. Do not add a hand-written native binding. Reselect current eligible files with the existing `fsWalkEntries`/safe-path machinery on every call, always `gitignore:true`, honoring parent/nested rules and negations, skipping symlinks. Hash selected source bytes before reusing persistent chunks, serialize only the same source index, restrict every result to currently eligible files, and prune missing/newly ignored paths only after complete traversal of their requested path/glob/hidden scope. Preserve other indexed scopes and all unseen paths after incomplete traversal. Persist AST chunks/file hashes plus a contentless SQLite FTS5 index as lucerna.sqlite under the same .mrmcp/search/<real-path-hash> directory used by document retrieval. Indexing limits/errors and `next_offset` must remain explicit, stateless and observable. No source/index/config files are written into Workspaces or the main SQLite schema. Persistent derived indices belong only in the application data directory and survive restart and operational-history cleanup. Recognize the public Lucerna extractors through SOURCE_CODE_LANGUAGES, including Go/C/C++/Zig/HTML/Python/YAML/PHP and the other common languages. Keep extension and filter aliases in MrMCP-owned code, retain uppercase .C as C++, and count detected languages without an extractor as unsupported rather than indexed empty files. Disambiguate distinct chunks sharing a Lucerna file/start-line ID deterministically before persistent insertion and retain the original ID in metadata.lucerna_id; never discard same-line symbols to satisfy a unique constraint. Grammar acquisition stays lazy in the public parser OS cache; do not modify vendor detectors or preload/download every grammar at startup. Test the real published MCP handler and the native parser from a standalone executable with an empty dependency cache before finishing.

- discovery/read: `fs_glob`, `fs_grep`, `fs_read`, `fs_navigate`, `fs_stat`;
- content mutation: `fs_write`, `fs_edit`, `fs_text_convert_encoding_eol`;
- structural mutation: `fs_mkdir`, `fs_copy`, `fs_move`, `fs_trash`, `fs_untrash`.

Do not reintroduce separate single-file/batch variants, a generic `replace` tool, permanent delete, filesystem transaction handles or server-side pagination/navigation state. Prefer these tools over shell commands, `uv`, Python or `js` whenever they express the operation directly. `TOOLS.md` is the human-readable contract and rationale for the published tool surface; keep it synchronized with descriptors and implementation behavior.

All filesystem navigation/search pagination is stateless. `fs_glob` orders paths deterministically in depth-first path-component order and resumes with the explicit `after_path` returned as `next_after_path`. Compare sibling names by locale with an exact string tie-breaker. Traversal, hard-limit collection and both filesystem cursors must use this same total order; never sort only an already-bounded page by a different flat-path order. A continuation may skip a completed subtree only when its component order proves that every descendant precedes the cursor. `fs_grep` resumes with explicit `{path,line}` `resume_after` / `next_resume_after`. `fs_navigate` receives the current line and direction for every file on every call. Never retain hidden server cursors for these tools. `fs_grep` consumes the shared traversal as an async iterator and stops at its result limit; use at most one additional path for lookahead when the current file is exhausted, and never pre-enumerate the remaining tree just to return an early page. Traversal failures remain separate from per-file decoding errors. Cursors refer to live data, not snapshots; do not imply isolation from filesystem changes between calls.

`fs_glob`, `fs_grep` and `fs_trash.selection` share one path-selection model: `path`, globstar `include[]`, globstar `exclude[]`, `gitignore` and `hidden`. `gitignore=true` applies applicable parent `.gitignore` rules and nested `.gitignore` files encountered while descending; do not imply support for Git's index, global excludes or `.git/info/exclude`. Do not add a separate recursive-gitignore switch or dependency-specific traversal policy such as `include_dependencies`. Include-based pruning requires proof from the active patterns that no descendant can match; any global/ambiguous pattern must fail open to the ordinary traversal. Cursor-based pruning additionally permits skipping subtrees proven to precede the continuation in component order. Never hard-code dependency/build/cache directory exclusions: users express those through `.gitignore` or explicit `exclude[]`.

Use explicit names that remain understandable in Tool Call logs. Text context counts are `context_lines_before` / `context_lines_after`, never generic `before` / `after`. Pagination fields identify what they resume (`after_path`, `resume_after`). Trash identifiers are `trash_id`, never generic `action_id`.

`fs_grep` must echo the effective `max_file_bytes` and return page-local `skipped_large_files` for candidates whose observed size exceeds that threshold. Do not count filtered paths, unvisited candidates or lookahead entries until actually examined, and never traverse ahead merely to compute skip totals. Preserve the existing `scanned_files` meaning (examined candidates after path resolution, including oversized files and later decoding failures) and document it explicitly. Per-file errors stay visible independently of oversized-file counts. Zero matches with skipped/error files must not be presented as complete search coverage.

Keep filesystem/retrieval text summaries concise and metadata-only: actual returned/succeeded/failed counts plus relevant continuation-field names. `structuredContent` remains canonical; never duplicate source text, match snippets, fingerprints or complete JSON in the summary, add persisted summaries, or infer success by searching nested payloads. Batch mutation summaries must expose partial/all-entry failures without changing existing call-level completion semantics. Descriptors should distinguish path discovery, textual search, known-file navigation and batched range reads; suggest small optional context when it avoids another read without increasing the default. Prefer suitable discovered catalog commands for symbol/caller/impact exploration; the existing Cymbal entry covers that role, and no LSP integration is needed. Verify skip counters, errors, pagination and summaries together through real tool dispatch, and compare complete verified client workflows when assessing call/output cost.

Support explicit UTF-8, UTF-16LE, UTF-16BE, Windows-1252 and Latin-1 directly in the ordinary text tools, including BOM and `LF`/`CRLF`/`CR` controls. Keep logical text separate from physical representation. The architectural goal is to minimize representation burden on the agent: infer/preserve every byte-level choice that is unambiguous from the source, normalize harmless differences in agent payloads, and require an explicit agent choice only for genuine ambiguity. Do not trade this convenience for permissiveness: malformed input, unsupported text and non-lossless conversions must fail rather than be guessed, substituted or silently repaired. `auto` decoding uses only the charset reported by pinned `chardet`. Settings → Files persists `text_encoding_detection=sample|full`, default `sample`, for `fs_read`, `fs_grep` and `fs_navigate`. Sample mode passes a zero-copy initial 16 KiB byte view (the whole buffer for smaller files) to `chardet`, then strictly decodes the entire original buffer. Use the first candidate returned by the public `chardet.analyse` API only when its confidence score is at least 80. If the candidate is absent, below that confidence threshold, has no charset, or full-buffer decoding fails, retry `chardet.detect` and strict decoding once over the complete original buffer. A sample can miss later charset clues even when decoding succeeds, so keep Complete file available. `fs_write`, `fs_edit` and `fs_text_convert_encoding_eol` always use complete detection whenever source decoding is needed, independent of the read/search setting; low-level decode/read helpers must default to complete detection so mutation callers cannot accidentally opt into sampling. Never use BOM, UTF-8-validity, UTF-16 structure or another local charset heuristic to choose/override a detected charset; fail if the final detection/strict decode fails. Explicit input encodings must bypass `chardet` rather than running detection and discarding its answer. Physical BOM detection remains MrMCP-owned and independent strictly to report factual recognized prefix bytes; never use it for charset selection and never infer it from the selected encoding. Decoder handling of a matching BOM is charset decoding semantics, not detection: custom Unicode decoders must match native `TextDecoder` behavior and consume an initial U+FEFF BOM. Native `TextDecoder` paths stay fatal on malformed input; never fall back to a permissive decoder merely because fatal decoding rejected invalid bytes. Charset-only `iconv-lite` fallback must prove lossless decode/re-encode byte identity before accepting input. Writes must likewise prove that final bytes decode through MrMCP's own path to exactly the requested text, and that requested physical BOM presence/absence matches the bytes, so unsupported characters or malformed Unicode never silently become `?`/replacement characters. Preserve a detected ASCII result as strict ASCII rather than converting it to UTF-8 or relying on the WHATWG `ascii` alias. Do not persist an out-of-band "intended encoding" for ambiguous byte streams: a new UTF-8 file containing only ASCII-compatible bytes may later auto-detect as ASCII, and the pinned detector remains authoritative. Treat BOM as a physical prefix invariant even for explicitly selected legacy encodings: `add` requires a BOM-capable Unicode encoding, but `preserve` on legacy text may succeed naturally when the encoded text itself reproduces the original recognized prefix; never prepend an extra Unicode BOM to legacy payloads. `output_encoding:"preserve"` reuses the detected source charset and defaults to UTF-8 only for a new file; `bom:"preserve"` preserves physical BOM presence and defaults absent only for a new file. `fs_write` must not decode an existing source gratuitously: require decoded source metadata only when preserving its charset, or when preserving line endings and the replacement actually contains breaks; raw BOM presence can be inspected without decoding. Fully explicit whole-file replacement must therefore remain possible even when old bytes are not decodable as text. Reads/searches normalize returned text to LF, never invent a trailing empty line solely because the file ends in a newline, and report empty files as zero text lines. Clamp `fs_read.end_line` to the actual line count before budgeting or iteration; never emit invented rows past EOF. Byte-bounded `fs_read` must prioritize the requested range over optional context: fill the budget with requested lines first, use only remaining space for `context_lines_before` / `context_lines_after`, and paginate only when the requested range itself is incomplete. Context must never displace requested content or cause `next_start_line` to repeat indefinitely; every continuation must advance beyond the requested start. Report `line_endings:"none"` for any text with no CR/LF separator, including both empty and non-empty single-line files. Incoming LF/CRLF/CR or mixed breaks from agent text are logical content only: do not reject them just for differing from the target style, because explicit `line_endings` must normalize all breaks and `preserve` must normalize them to an existing uniform source style. For a new file, `line_endings:"preserve"` defaults to LF and must normalize any incoming LF/CRLF/CR/mixed separators to LF. If an existing source is mixed, return `mixed_line_endings` when a preserved result has breaks; if an existing source has `line_endings:"none"` and the result introduces breaks, return `line_endings_required` and require explicit `lf`, `crlf`, or `cr`. If the resulting text has no breaks, allow `preserve` even for mixed/new/none because the output style is unambiguously `none`. Tool string arguments are already JSON-decoded text: never apply a second C/JavaScript-style escape-decoding pass.

Every tool that reads regular-file content for `fs_read`, a matched `fs_grep` file or `fs_navigate` returns an opaque whole-file `fingerprint`; `fs_stat` may compute one when explicitly requested. Mutation tools accept `expected_fingerprint` per file and return a structured `fingerprint_mismatch` result instead of writing when the current bytes differ. Treat the fingerprint as an opaque concurrency token, not as a public SHA-256 contract even if SHA-256 is the current implementation.

Batch filesystem entries are independent. Do not expose `atomic`, do not roll back successful earlier batch entries because a later entry fails, and do not pretend filesystem operations form an OS transaction. Return structured per-entry status plus `succeeded`/`failed` counts so the agent can see exactly what happened. A single recursive copy/move/trash/untrash may report `failed_partial` when the destination/payload exists after failure; leave that state visible rather than attempting a second best-effort rollback operation. Recursive copy and the cross-filesystem move fallback must preserve symlinks as links rather than dereferencing them.

`fs_edit` is the important local exception: each file is internally all-or-nothing at the edit-validation level. Read the file once, verify `expected_fingerprint` against that initial version, normalize the in-memory edit representation consistently, apply its `edits[]` sequentially to the evolving document so edit N sees edits 1..N-1, validate every `expected_occurrences`, and only then write that file once. If any edit validation fails, do not write that file; continue independently with other files. Duplicate file entries are invalid. Successful results report compact ordered `{index, expected_occurrences, occurrences}` metadata without echoing potentially large `old_text`/`new_text` values.

Filesystem removal is trash-only. There is exactly one MrMCP metadata directory, `APP_DIR/.mrmcp`; named Workspaces never receive a `.mrmcp` directory from MrMCP. `fs_trash` accepts explicit paths and/or one structured selection, collapses nested selected targets, and stores physical payloads from every Workspace under the single `APP_DIR/.mrmcp/trash/<trash_id>/` directory. `trash_id` values are globally unique across both SQLite metadata and payload directories and use local date/time to the second with a numeric suffix only on collision. Before moving payloads, insert the transaction and item metadata in SQLite so original absolute paths, deterministic payload names, cached type and cached non-directory byte size remain diagnosable; directory size stays unknown even if a later move/crash leaves a missing or partial payload. Do not write sibling JSON manifests. Normal move failures with no retained destination remove their item metadata; retained partial destinations keep it. `fs_untrash` is Workspace-scoped, restores available payloads independently, deletes metadata only after a successful restore, and leaves missing/failed item rows visible for retry/cleanup. Remove a transaction only when no tracked item rows remain. Exclude only the real `APP_DIR/.mrmcp` metadata directory from trash targets/selections; a same-named directory inside an unrelated Workspace is not MrMCP metadata. `fs_trash` and `fs_untrash` are intentionally non-destructive in MCP annotations. Tool Call logs are diagnostics only.
